# LL(1) 与 LALR(1)：本工程里的两套前端与算法对比

这份文档回答一个问题：**同一门语言（pl0-super），三种前端实现各自是什么、适合什么。**
三者在同一份样例上可执行地对照：

| # | 实现 | 算法 | 前端代码 | 依赖 | 产物 | 端到端（2007 行，5 次） | 前端编译（`-O2`） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① | [`lalr1/`](lalr1/README.md) **默认前端** | LALR(1) 表驱动：LR(0) 项集 + 1 个展望符 + 同核合并，**自底向上移进-归约** | `pl0-super.gram`（文法 + 语义动作；机器产出 3940 行解析器） | 要 ParseEngine | `build/pl0-super`（2,055,291 B） | min 20.7 / avg **21.3 ms** | **801 ms** |
| ② | **LL(1) 表驱动**（生成器产物） | LL(1)：FIRST/FOLLOW → 预测表 → 栈式预测分析 | 同一份 `.gram` 换成 `--mode ll1` | 要 ParseEngine | — | — | — |
| ③ | [`ll1/`](ll1/README.md) | **手写递归下降**（LL(1) 的**直接编码**：预测表的分支写进函数，不建表） | `lexer.cpp` + `parser.cpp`（1050 行，人写） | 只要 `g++` | `build/pl0-super-lib`（1,202,195 B） | min 18.5 / avg **19.6 ms** | 441 + 1206 = **1647 ms** |

三者的关系（关键，别混）：**② 和 ③ 是同一个算法的两种落地**——② 建一张
$M[A,t]$ 预测表、用一个显式栈跑；③ 把同一张表的分支**直接写进递归函数**
（本工程 `parser.cpp` 里 `parseAdd`/`parseMul`/`parsePrimary` 的调用链就是优先级层的编码）。
所以 ③ 是否"算 LL(1)"取决于文法：**只要那份文法本身是 LL(1) 的，递归下降与表驱动预测分析
接受的语言完全一样**；差别只在实现代价与运行常数（③ 省掉建表与查表，多一层函数调用）。

而 ① 是**另一类算法**：自底向上、能接受更大一类的文法（含左递归、可用优先级声明消解二义）。

三份前端产出的"简化代码"结构相同，后面接**同一套库**（`simplify.cpp` / `codegen.cpp` / `vm.cpp`），
所以样例只用一批、`check.sh` 逐字比对输出。

## 1. 两种算法在做什么

### LL(1)：从开始符号往下推

给每个候选产生式算"该不该用"：

$$
SELECT(A\to\alpha) =
\begin{cases}
FIRST(\alpha)\cdot FOLLOW(A), & \alpha \Rightarrow^* \varepsilon\\
FIRST(\alpha), & \text{否则}
\end{cases}
$$

同一格 $M[A,t]$ 只能命中一条产生式，否则文法不是 LL(1)。分析时栈顶非终结符 + 当前记号决定
用哪条产生式；**递归下降**就是把 $M[A,\cdot]$ 的分支写进函数（本工程的 `parseAdd`/`parseMul`…）。

### LALR(1)：把输入往上归约

LR(0) 项目做闭包/转移得到自动机，每个项目带 1 个展望符得到 LR(1)；**核心相同**的项集合并
（这是 LALR(1) 与 LR(1) 的唯一区别，表小一个量级）。分析栈里是"状态 + 已识别符号"，
按 ACTION 移进或规约；规约时执行产生式上的动作。

## 2. 文法要求：本工程拿到的三条真实证据

**证据一（LL(1) 表驱动的硬限制）**：把 `lalr1/pl0-super.gram` 直接换成 `--mode ll1` 生成，被拒：

```text
错误：文法不是 LL(1)：M[expr__tail, AND] 同时对应
      expr__tail -> AND expr expr__tail 和 expr__tail -> %empty
```

我的表达式文法是**二义**的（`expr → expr OP expr`），在 LALR(1) 里靠
`%left OR / AND / 比较 / 加减 / 乘除模` 在生成期消解；**LL(1) 没有优先级声明这种东西**，
必须把表达式**分层**（`expr → term expr_tail`、`term → factor term_tail` …）——二义用结构
消解，而不是用声明。这也说明 ② 想落地，先得把 **`expr` 那一层改成无二义的分层写法**。

**证据一′（递归下降为什么能跑同一门语言）**：③ 手写的 `parser.cpp` 之所以不需要改文法，
是因为它**没有要求文法"是 LL(1) 形式"**——它把优先级直接写在函数分层里（`parseAdd` 调
`parseMul`，`parseMul` 调 `parseUnary`…）。这在形式上就是"已经改造过的预测分析器"：
文法经过分层后是 LL(1) 的，而分层这件事由人写死在代码里。换句话说，
**② 需要的文法改造，在 ③ 里换成了代码分层。**

**证据二（LALR(1) 与 LL 都要面对的经典冲突）**：悬挂 `else` 在经典做法里用
`%nonassoc THEN` + `%left ELSE` 消解；本工程索性**强制语句块**（`if/while/for` 的分支文法上
只能是 `block_stmt := BEGIN stmts END`），冲突在文法结构上就不存在——这条对两种算法都成立，
是"改文法比加声明更省事"的例子。

**证据三（左递归）**：`LALR(1)` 能直接吃 `stmts := stmts stmt` 这种左递归；LL 家族不能，
必须消除左递归（生成器 `%mode ll1` 会自动做，产物里能看到改写出来的 `expr__tail`）。
递归下降这边同样是"用循环代替左递归"：`parseStmts` 里 `while (…) { parseStmt(); }` 就是
左递归消除后的形状。

## 3. 表与内存

| | ① LALR(1) 表驱动 | ② LL(1) 表驱动 | ③ 手写递归下降 |
| --- | --- | --- | --- |
| 表 | ACTION/GOTO（状态 × 终结符/非终结符） | 预测表 $M[\text{非终结符},\text{终结符}]$ | **不建表**：分支写进函数 |
| 项集/状态 | 有（可到几百个，`RESULT.md` 里能看到） | 无 | 无 |
| 本工程实测 | 可执行 2.06 MB | —（未落地） | 可执行 1.20 MB |
| 解析开销 | 查表 + 状态栈 + 语义值经池子间接寻址 | 查表 + 显式栈 | 递归调用 + 直接分支（最快） |

差值就是这 ~8% 端到端与约 0.85 MB 体积的来源（见开头表格）。

## 4. 错误与恢复

| | ① LALR(1) 表驱动 | ② LL(1) 表驱动 | ③ 手写递归下降 |
| --- | --- | --- | --- |
| 报错时机 | ACTION 格为空 | 预测表查不到 | 当前记号不在任何分支里 |
| 信息质量 | 报状态与记号；更细的信息要自己维护上下文 | 天然知道"期望什么" | 最容易写具体（本工程 `parser.cpp` 的 `fail("if 的分支要用 begin … end 包起来")`） |
| 恢复 | 标准做法：`error` 产生式 + 弹栈找到可移进项，**报错后继续解析**（仓库实验三 [`../lab_report_axhu/lab3_parser/`](../lab_report_axhu/lab3_parser/) 用它做到"坏语句后面的代码仍进树"） | 要自己写同步集合 | 同 ②，且能在函数里就地决定跳到哪里 |

## 5. 实现与维护成本

| | ① LALR(1) 表驱动 | ② LL(1) 表驱动 | ③ 手写递归下降 |
| --- | --- | --- | --- |
| 加一个运算符 | 加一行 `%left` + 一条产生式（声明式） | 还要保证分层后 SELECT 集不相交 | 改对应优先级层的函数（动代码） |
| 加一条语法 | 加一条产生式 + 动作（每个备选都要写动作） | 加一条产生式 + 保证 LL(1) | 加一个分支/函数 |
| 改文法后 | 重新 `make grammar` | 重新 `make grammar` | 直接重编 |
| 前端编译时间 | **801 ms**（一个大文件） | 同 ① | 1647 ms（两个文件，递归下降的内联多） |
| 依赖 | ParseEngine | ParseEngine + 文法必须先写成 LL(1) | **只要 `g++`** |
| 调试 | 看项集/状态与 `RESULT.md`，不直观 | 表 + 栈，比 ① 直观 | 调用栈 = 推导过程，最直观 |

## 6. 选型建议（本工程为什么两个都留）

- **要"文法天然、二义好消解、错误可恢复"**（本工程默认）：用 **① LALR(1)**——左递归直接写、
  优先级用声明、`error` 产生式能恢复；代价是要生成器、产物大、调试看状态。
- **要"零依赖、产物小、错误信息具体、跑得最快"**：用 **③ 手写递归下降**——代价是文法必须
  是人改造过的（表达式分层写进代码）、加运算符要改代码、错误恢复要自己写同步集合。
- **② LL(1) 表驱动**在两者之间：它有 ③ 的"文法必须是 LL(1)"与 ① 的"要生成器、要建表"，
  换来的是"不用手写函数分层，改成声明式文法"。本工程把它作为**对照项**保留：文法改成
  分层表达式之后 `--mode ll1` 就能出这份前端。
- **三者并存的理由**：pl0-super 用 `lalr1/` 证明"同一门语言能用声明式文法写下来"，用 `ll1/`
  提供**不依赖生成器**的可跑基线与最快的实现；两条路径输出由同一批样例逐字比对，任何一边
  改错都会在 `make check` 里暴露。
- 更远一档的算法（`lr1` / `ielr`）在本工程没用到：现在这份文法 LALR(1) 就够；
  需要 LR(1) 的场合是"LALR 合并引入了归约/归约冲突"。同一份文法换个 `--mode`
  就能试：

  ```sh
  ../../build/bin/ParseEngine --grammar-file lalr1/pl0-super.gram --mode ielr --out-dir build-ielr --lang cpp17
  ```
