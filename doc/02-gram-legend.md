## 阅读前：一分钟看懂这个故事

**ParseEngine 是什么？**

你可以把它想成一台“语法说明书翻译机”。

- 你写一份 `.gram` 文件，里面是语法规则，比如“表达式可以怎么加减乘除”。
- 它读进去，能生成八种语言的解析器代码：C99、C++17、Python、C#、Rust、Go，以及范围较窄的 Java、JavaScript/TypeScript。
- 解析器的作用，是让程序“读懂”一段文本。
- 它还能只输出一份分析报告，不生成代码——这一档叫 `--lang gram`。

**它有多厉害？**

一份 `.gram`，十六种生成模式，八种目标语言，外加一个只要文法与分析报告的导出档。

**谁写的？**

糖糖，白天上班，晚上回到住处写。搭档是 AI：Codex、DeepSeek/GPT6，后续还有 30x GPT 账号。人定方向，它们实现，人验收。

**大学背景改成了什么？**

大学那门编译原理，老师只教了：

- 词法分析的全部；
- LL(1)；
- LR(0)；
- 四元式 DAG 图化简。

其他没讲。糖糖当年考试分数很高，但高分不等于自己把地图外的地方走过。`ParseEngine` 就是他回去补那半张地图。

**结果可以复查。** 文中的模式、语言、模板数量与回归结果，以当前源码、测试、
`AGENTS.md` 和 [`15`](15-language-mode-support.md) 为准。

## 第一章 先说结果：一份 `.gram`，六种语言

糖糖用业余时间写 `ParseEngine`：晚上回到住处，坐到那张折叠桌前。

**写这个解析器生成器，是真的爽。**

白天的时间总是被切得很碎；晚上坐到自己的折叠桌前不一样——一句话进去，一张表出来，一百多个状态整整齐齐排在那儿，冲突一行一行被消解掉，`make -C source test-smoke` 从头绿到尾。

那种感觉很难形容，大概就是：**我写的这个东西，天下第一。**

不是狂妄，是那三个月的真实体感。

一份 `.gram` 写下去，C、C++17、Python、C#、Rust、Go 六种语言一起出；LL(0) 到 CYK 十六种模式，按各档支持范围选用；`RESULT.md` 把 FIRST/FOLLOW、项集、冲突与消解过程一条条摊开给你看。

> **说人话旁白：**  
> FIRST/FOLLOW 是两张“猜开头、猜后面”的表；项集是“现在读到哪一步”的所有可能性；冲突是“同一格有两个选择，工具要决定选哪个”。别家的工具只报一句 “conflict”，它直接告诉你冲突在哪个状态、哪两条产生式、怎么改；`--teach` 还会把消解过程讲一遍。

写到后半夜最上瘾的一刻，是看着自己早上随手写下的那份 `.gram`，被工具变成一份**能编译、能跑、能进仓库**的解析器。

那种“我一个人把整个链条打通了”的感觉，够他撑过很多个深夜。

住处很小，一张折叠桌，一把椅子，一台自己攒的台式机。机箱风扇一跑满就像要起飞。项目夹在 `D:\Desktop\ParseEngine`，`git log` 里很多提交是深夜。仓库挂在 GitHub 上，起初挂 Apache-2.0、后来换成了 MIT，README 写得很短：

> 一份 `.gram`，十六种生成模式，六种目标语言，外加一个只要文法与分析报告的导出档。

Star 数：3。其中两个是他自己点的。

这些代码**没有被别人真正看过**。没有导师过目，没有评审会，也没有验收——没有人知道他在写这个；晚上那间屋子里，只有他、一个终端，和屏幕另一头的 AI：**Codex 与 DeepSeek/GPT6**；后来增量解析收口，又接上了 30x GPT 账号。

分工很简单也很稳：他定方向——要哪些模式、出哪几档产物、冲突怎么才算处理对；它们实现——模板、后端、测试、文档；他验收——`make -C source test-smoke` 从头绿到尾、`RESULT.md` 一个字一个字对。

三个月里“看过”这套东西的，只有他们三个。

所以那句“天下第一”听起来像狂话，其实不是跟谁比。**是一个人自己推出整张表、自己把几个后端一个个跑绿之后，才会长出来的那种确定感**——没有人点头，也不需要谁点头。

那天深夜，他准备关电脑，又把 `--lang gram` 那一档跑了一遍：导出的 `.gram` 与输入逐字节相同，`calc.analysis.md` 里摊着这次生成的全部依据。他盯着那行结论看了半秒，笑了一下——不是给谁看的笑。

## 第二章 再说来路：大学只教了半张地图

——第一章那份爽里，有一部分是在补地图。

大学那门编译原理，老师讲得不算差，但覆盖得很窄：

- 词法分析讲全了：正则、NFA、DFA、最小化、词法表；
- 语法分析只讲到 LL(1) 和 LR(0)；
- 中间表示只讲到四元式和 DAG 图化简。

再往后的 SLR、LALR、LR(1)、IELR、LR(k)，以及冲突消解、数据流、SSA、寄存器分配、代码生成，老师都没讲。

考试他分数很高。卷面上教过的部分几乎都会：FIRST/FOLLOW 会推，LL(1) 预测表会填，LR(0) 项目集闭包会算，四元式 DAG 会画会化简。

可那门课对他来说始终是：**老师画过的那半张地图，我背得很熟；地图外面是什么，我没走过。**

`ParseEngine` 就是他回去把地图外面的那半张表从头算了一遍：

- 从 LL(0) 到 IELR 多种模式；
- SLR / LALR / LR(1) 自己推；
- 项集自己闭包；
- 冲突自己一条条看；
- `--teach` 把消解过程写进报告；
- 算完表还要出代码——多档产物各自 `build`、`run`；
- 三个运行时（LL / LR / `lex`）在测试里对同一份输入比结果。

**当年那门课没讲到的部分，他一个人补完了**——而且这一次，每一张表都能重算，每一处冲突都能解释。

> **说人话旁白：**  
> LL 像“从上往下猜”，LR 像“从下往上归约”。老师教了 LL(1) 和 LR(0)，相当于只教了两种最基础的读法。SLR、LALR、LR(1)、IELR 是更细、更强的读法。糖糖后来把这些都补上了。

### 补记：那张地图上，不止他一个人

补地图补到一半的时候，糖糖有一天在网上翻资料，翻到了南京大学编译原理课程的实验文档。附录 A 里明明白白写着一门叫 **C—** 的语言：Tokens、High-level Definitions、Specifiers、Declarators、Statements、Local Definitions、Expressions……一份完整的、从零手搓编译器的实验框架。

他愣了一会儿。

不是羡慕。是那种“原来地图外面不止我一个人在走”的愣。

南大的同学在课上被要求写 C— 的编译器——词法、语法、语义、中间代码、目标代码，一条龙。而他在住处，没人要求，自己给自己加戏，从 `.gram` 推到六种后端，从 LL(0) 推到 IELR，又从四元式那条失败线退回来，换到 `pl0-super`，最后还嫌不够，开始写 Magel 语言。

方向竟然撞上了。

南大是“被要求手搓 C—”，他是“自找麻烦手搓 Magel”。一个在课程里，一个在住处；一个有评分标准，一个只有 `git log` 里深夜的提交。但两拨人干的事，本质上是一件事：**把一张地图从“老师画过的那半张”推到“自己能重算的整张”。**

他把那份实验文档存进了书签。没跟任何人说。

只是那天晚上写 Magel 语言的时候，心里多了一点很轻的底气——**原来这条路上，还有别人。**

## 第三章 失败账单：四元式中间层

这一篇不是爽文。这一篇是账单。

把生成器写顺之后，糖糖觉得这条线“太浅”了——他想要一个**真正的编译器后端**：源码先进中间表示，中间表示上做数据流、SSA、寄存器分配，再出目标代码。

> **说人话旁白：**  
> 中间表示就是“先把程序翻译成一种通用便签”。四元式像一条条 `x = y + z` 的便签。SSA 是“每个变量只赋值一次”的形式。寄存器分配是“把变量塞进 CPU 的小格子”。这些听起来很高级，但不一定划算。

于是仓库里多了一个 `library/transfer`：五块合成一个库（`irbridge` / `core` / `dataflow` / `ssa` / `regalloc`），一个命令行 `t1t`，一条端到端流水线。后来又长出 `typebuild`（类型树、泛型、接口、运算符重载）与 `astbuild`（AST 标注 + 降级）——**这两个子库后来也删了**：四元式优化引擎留着用，扁平化那条路不要。

那一夜，他是这么过的：

```text
$ t1t-example-suite … mips
[失败] 23_pointer_array.quad —— 期望 1 20 2 2，实际 1 0 2 2
$ t1t transfer 24_pointer_compare.quad
t1t transfer: 第 35 条四元式的操作 '!' 不存在（未知四元式）
$ t1t transfer 29_literal_cast.quad
t1t transfer: Read of uninitialized variable: t10
```

一条一条查下去，最后挖出来的都不是“算法不够高级”，而是**分层本身在漏**：

- 指针的 tag 是按“每个指针自己的基列表”编号的，结果 `q = &b[1]` 和 `ps` 的列表对不上，分发链拿 `0` 去查，落到 `a` 那一支——读到从没写过的 `a[1] = 0`。修法是把 tag 换成**全局按基名编号**。跟后端一点关系都没有。
- 后端优化器有三处**自己**的缺陷：两条并行向量上的常量传播 + 死代码删除会折叠出错误结果；`cvt` 被折叠成字面量时**没按目标类型截断**；常量传播删掉 `t1 = t0 + 0` 这种临时量的定义，却漏掉“赋值语句源操作数”这个位置。于是好几个示例只能写 `# 优化: 否`，等于绕开优化器。
- 同一个语义要在**两个地方各写一遍**：运算符重载要写标注期决议 + 降级期发调用；泛型要写类型实例化 + 函数体单态化；指针要写类型层的 `*T` 与降级层的“基 + 下标”。
- 每修一个端到端样例，要同时理解四五个层次；验证还得自己写两份最小 `.quad` 复现。

天快亮的时候，他盯着那条流水线，说了句很难听但很对的话：**成本来自 IR，收益没有兑现。**

分层本来是为了“一次分析、多处复用”，可主线是单线程 + 静态绑定的地址模型，那些分析一个都没用上；而真正挡住样例的，是优化器自己的缺陷。

于是他做了两件事。

第一件，把这条线**收住**：`library/transfer` 保留当研究、教学与实验用，不再是主线；复盘就是上面这段经历。

第二件，**换路线**：新开一个 `project/pl0-super`——**不建中间表示**。文法归约时就把“简化代码”建进池子，只做四趟能一句话说清、能量出次数的化简（常量折叠 / 代数化简 / 死分支 / 窥孔），然后直接发栈式目标机汇编，用自带的解释器跑出结果：

```text
$ pl0-super --stats samples/simplify_demo.p0s
简化：折叠 6，代数 2，死分支 3，窥孔 2
46
```

顺手还把“两种前端”摆在了同一门语言上：`lalr1/` 是生成器出的 **LALR(1) 表驱动**，`ll1/` 是**手写递归下降**。同一份文法直接换成 `--mode ll1` 会被拒：

```text
错误：文法不是 LL(1)：M[expr__tail, AND] 同时对应
      expr__tail -> AND expr expr__tail 和 expr__tail -> %empty
```

——`%left` 优先级在 LL(1) 里没有等价物，表达式必须分层。这条报错、三种实现的实测数字，都写进了 `project/pl0-super/语法分析对比.md`。

最后留下的不是一条失败分支，而是一份可复现的路线判断：判定失败、换路线，再把两套前端跑绿。

### 本章补记：这一章为什么值得写

- 第一章讲的是“怎么赢”；这一章讲的是“怎么承认输了”。
- 三处优化器缺陷、一处降级器的 tag 编号、一遍多余的解析——每一条都是**能复现、能定位、能写进文档**的。
- 失败不是白花的钱：`typebuild` 的类型系统、`astbuild` 的缺口清单、指针联合地址模型、泛型函数单态化、运算符重载降级，以及那个“四元式 vs 直接出码”的取舍结论，都是这一段买来的。
- 一句话总结：**当你发现自己在给一层抽象写第二份实现、而收益还没出现时，先怀疑那层抽象是不是该存在。**

—— 第三章 · 完

## 第四章 大扫除：把多余功能删掉

第二天晚上，他没有急着加新功能，先把仓库从头到尾数了一遍。

数出来的家当很唬人：语言后端**七套**——C99、C++17、Python、Rust、Go、Java、C#；生成模式**十三种**；外加一组只给语法树贴标记的 `%ast_*` 指令。

然后他**想通了**一件事：这些不是战功，是账。

功能不会自己待着不动，它每天都要人喂——一份模板、一份 `RESULT.md`、一条冒烟分支、一章文档。开出来的每一档，都是一笔要一直还的利息。

问题是数字对不上。README 上写着「五种目标语言」「十三种生成模式」「120 个（文法,语言）组合」，可代码只认四种、十二种、97 个组合。谁照着 README 敲一句 `--lang java`，得到的是一句「未知的目标语言」。

「文档在骗人。」他在交接单上写。

「不是文档坏了，」屏幕另一头回了一句，「是每多一套后端，就多一份要同步的清单——生成器、模板、`RESULT.md`、冒烟分支、文档章节、编辑器下拉。七份清单里，总有一份落后半步。」

于是开始删。

Rust 和 Go 当初都是照着 C# 后端改出来的“方言后端”：模板骨架相近，换一层语法皮。Rust 那一档先收掉——不是它不好，是当时主线用不上，留着就要多养一份模板、一份 `RESULT.md`、一条冒烟分支；示例库里还躺着一整个 Rust 工程（五百多个文件）。Go 也收掉，理由更直接：**应用面窄，来问的人少，维护成本却不低**。删，注释也改干净。

Java 后端跟 C# 后端是一对双胞胎，但删它的理由不是“双胞胎”。Java 对写死在代码里的常量有硬限制：**常量池里单个 UTF-8 常量最多 65535 字节，方法字节码也有 64KB 上限**。ParseEngine 生成的大 DFA 表、大模板、大字符串常量，很容易一不留神就撞线。它不是“不想支持”，是这门语言的载具对“把大表直接写成常量”这件事不友好。删。

> **说人话旁白：**  
> Java 的 class 文件里，写死的字符串和常量像贴了张“最多 64KB”的标签；生成器吐出的大表一大，就塞不进去。  
> Go 则是另一个问题：不是塞不下，是用的人少，养它不划算。

`%ast_skip` / `%ast_fold` / `%ast_label` 只生成了几个查询函数，从来没接进建树——用的人会以为有 AST，其实什么都没有。**死代码比没有更坏，因为它看起来能用。** 删。

GLR 有自己的 GSS 运行时、自己的错误恢复路径，写完以后没人用过。删。

一刀下去五万行。剩下的四种语言、十二种模式、97 个（文法,语言）组合，全跑一遍。

「跑了多久？」

「一分钟。」

他盯着那份全绿的报告看了一会儿，忽然说：「还有一件反的。」

「哪件？」

「C++17 那一档，我把它退回拼接式了。」

「模板引擎不是刚迁完？」

「迁完才发现，模板化之后生成器里看不见产物长什么样了——想看一份 `parser.hpp`，得先渲染一遍。产物模板本来就是给人改的，`__MODE_NAME__` 明文摆在那儿，改起来最省事。」

「那引擎呢？」

「留着。它是纯头文件、不依赖别的库，谁想快速拼一段 DSL、拿模型渲染文本，直接拿去用。工具是好工具，只是不该由生成器扛着。」

顺手把产物模板从仓库根目录挪进 `source/templates/`——「藏得深一点」，省得根目录一眼看去全是模板。

—— 第四章 · 完

## 第六章 五个 Agent 和一棵树：多人共用一张桌子

尾声写完之后没几天，糖糖干了一件自找麻烦的事：他**同时开了五个 agent**，一人一档后端——C99、C++17、C#、Python、Rust——**改的是同一棵工作树**。

> **说人话旁白：**  
> agent 就是 AI 助手。工作树就是同一份代码文件夹。五个 AI 同时改同一份文件夹，就像五个人同时在一张桌子上切菜、炒菜、摆盘，谁一抬手就可能碰到别人的盘子。

四小时后他在 `AGENTS.md` 顶上补了四条规矩。下面是那四条规矩的来处。

### 第一个照面：把别人的模板一起内联了

「喂——我 C# 怎么全炸了？」

A 在改 C99，顺手敲了 `make -C source templates`。可 `make -C source templates` 会把 `source/templates/` 下**所有人的**模板一起内联进 `source/src/templates_data.cpp`——包括 B 十分钟前刚写下、**还没来得及改 `code_gen_csharp.cpp`** 的那十八份 `csharp_*.tmpl`。

于是 B 的产物里全是没替换的 `{{ mode_name }}`，三十六个 `.csharp` 目录全红。B 第一反应是自己写错了，查了半个多小时。凶手就坐在隔壁，还一脸无辜：「我这边产物逐字节没变啊。」

> **规矩一：编译要上锁。**  
> 共享生成物谁都不许在别人编译时动。于是有了 `tools/lock.sh`——锁是 `tmp/build.lock` 这个**目录**，里面记着是谁、什么时候、为什么锁的。编译时持锁 → 编译出错继续持锁 → 错误处理完、编译绿了才放锁。

### 第二个照面：替别人提交

`git status --short` 一敲，第一列躺着**四十条别人的** `A` / `R`。

谁手一滑敲个裸 `git commit`，就把别人的半成品一起提交了，提交信息还署自己的名。

「我没写过 C#。」  
「可你提交了。」

这顶帽子谁都不想要——尤其是那个提交里还夹着别人**改到一半、根本编不过**的文件。

> **规矩二：提交按路径。**  
> `git commit -m "…" -- <自己的路径>`，不许 `git add -A`、不许 `git commit -a`。暂存区是共享的，带路径提交只落自己列出的那几个；共享生成物用**隔离树里生成的那份**，免得把别人还没落盘的模板一起内联进去。

### 第三个照面：三小时

这一回合最惨。

有人跑了**全语言冒烟**。C# 每份产物都要起一次 MSBuild + NuGet，Rust 每份起一次 cargo——一轮冒烟从“几分钟”变成**三个小时**。旁边那个 agent 的活早就写完了，只能干等，从午夜等到快三点。

它后来在提交信息里留了一句：

> 我不是在等编译，我是在等**别人**编译。

> **规矩三：验收分三档，别一上来就跑最贵的那档。**  
> 秒级（`tools/quick-verify.sh`：约 24 秒）→ 分钟级（增量隔离构建，约 36 秒）→ 提交前跑一次全量（只跑自己那一档）。  
> 还有一条更省时间的：**`diff -r` 为 0 就不必再冒烟**——产物一个字节都没变，编译结果不可能变。
>
> **规矩四：默认只跑自己那一档。**  
> `GEN_ALL_LANGS=c` / `SMOKE_LANGS=c`。全 5 档 111 个组合要 1 分 54 秒，只跑 C 档 36 个组合 **53 秒**。全档全量是奢侈品，只在合并前用。

### 还有两个让人笑出来的坑

- **「未知的目标语言 rust」。** 某人拿一棵旧 `HEAD` 的树和一棵新 `HEAD` 的树做基准，`diff` 里冒出一堆跟自己毫无关系的差异——因为**两棵树中间，别人把 Rust 后端提交了**。
- **`VAR=x cmd` 的前缀会被静默丢掉。** 某人以为自己在测「编译失败时保留锁」，结果跑的是正常编译，白等一轮。后来一律写 `env VAR=x cmd`。

### 收场

那天最后统计了一下：**五档后端、252 份模板、109 个（文法,语言）组合**，一棵树上同时躺着五个方向改出来的产物——逐字节比对，**0 差异**。

一个人 + 一个 agent 是结对；五个 agent 就是一支队伍。而队伍最难的不是分工，是**共用同一张桌子**。

糖糖把结论写成了三句话，放在 `AGENTS.md` 的最前面：

> **编译要上锁，提交按路径，验收先跑秒级那档。**

## 第七章 换一台引擎：Rust 那一档

Rust 后端加回来的时候，词法是照着 C99 那套写的：生成期把每条正则编成 DFA 表，产物里放 `Dfa` 常量 + 256 项的字符类映射，运行时查表。产物不带任何依赖，编译最快。

「为什么不用 Rust 自己的正则库？」

「因为那套是给 C 写的。」他敲了一行，「顺手跟着用了。」

后来 Rust 那边的正则越来越花：`{1,100}` 这种超出 32 上限的写法、否定类和分组加星号搅在一起——生成器自带的那台编译器先报了错，报得还很有道理：「重复次数不能超过 32」。可 Rust 的 `regex` 明明收。

于是改了：`%token regex` / `%identifier` / `%commit` 的模式**原样交给 Rust 官方的 `regex` crate**，产物里的 DFA 表整套删掉，三张表在第一次取 Token 时各编译一遍。

顺手把「自带编译器认不下」这件事重新分了类：**只有 C99 还是硬错误**——它真的要用那份 DFA 编表；其余四档把正则原样交给各自语言的正则库，认不下就**打一条警告**，生成照常往下走。

改完那天，109 组产物前后各生成一遍：C99 / C++17 / Python / C# **一个字节都没动**，Rust 那一档十二个用例重新编译、重新跑、跟 `example/*.expected` 对得上。

「所以这回省了什么？」

「省了一个『我以为是方言差异、其实是自家编译器太小气』的坑。」

最后，我删掉了那一版 `AGENTS.md`，把规矩收进项目文档，宣告这一阶段收尾。

## 第八章 给 Magel 语言装上对象表：值放在哪儿

正文里说「第四章写减法的部分」——删掉长歪的后端、删掉没人用的模式，把项目收瘦。但那只是**减法**。真正让糖糖兴奋的是后面这一段：他回头把 `magel`（Magel 语言）从早期「能算数的 C 子集」原型推成「能写数据结构与字符串处理的 C 风格虚拟机语言」，而且中间**每一处都踩在“表示”上**——和第三章那句「表示选错，后面每一步都在还债」正好接上。

### 先解释一下：这个 Magel 不是 Minecraft

每次他跟别人说“我在写一个 Magel 语言”，对方第一反应都是：

> “Minecraft？你要写模组？”

糖糖一开始还耐心解释：“不是，是 Magel，早期原型借了 C 的语法。”后来他放弃了，改成一句自嘲：

> “对，就是 Minecraft 的 Magel。我在里面挖矿——挖的是内存。”

> **说人话旁白：**  
> Minecraft 里你要挖方块、合成物品、管理背包、防苦力怕。  
> 编译器里你要管内存、拼字符串、分配对象、防内存泄漏。  
> 糖糖后来发现，这两件事的焦虑感惊人地相似。

### 差点叫 C+- 的那一晚

这一段开始之前，糖糖有一个一直没敢公开的冲动：他想把 Magel 语言改名叫 **C+-**。

原因很直白：它不是 C，它只是 C 的一个子集——减掉了指针算术、减掉了预处理器、减掉了那些“你能写但我不保证”的东西；同时又加上了字符串、容器、大整数、对象表。

“C 加一点，减一点，不就是 C+- 吗？”他在 README 草稿里敲下这三个字符，又删掉，再敲，再删。

最后没改。因为 `magel` 已经叫顺了，而且他怕别人以为这是个玩笑项目。

但那一晚，他在提交信息里留了一句：`// 差点叫 C+-`。

后来这句话被删了。只有他自己知道，Magel 语言曾经离 C+- 只有一次 `git mv` 的距离。

> **说人话旁白：**  
> 如果真叫 C+-，搜索引擎会以为你在找 C++ 的错别字。  
> 如果叫 Magel，搜索引擎会以为你在找 Minecraft。
> 糖糖最后选择了一个**搜索引擎和人类都会误解**的名字，然后继续写代码。

### 南京大学的 C—，和他的 Magel

就在 Magel 语言推到“字符串搬上堆”那一晚，糖糖又点开了那个存了很久的书签——南京大学编译原理课程的实验文档。

附录 A 里的 C— 语言文法，他之前只看了一眼。这次他一行一行读了下去。

> Tokens：INT、FLOAT、ID、SEMI、COMMA、ASSIGNOP、RELOP、PLUS、MINUS、STAR、DIV、AND、OR、DOT、NOT、TYPE、LP、RP、LB、RB、LC、RC、STRUCT、RETURN、IF、ELSE、WHILE……
>
> High-level Definitions：Program → ExtDefList；ExtDefList → ExtDef ExtDefList | ε；ExtDef → Specifier ExtDecList SEMI | Specifier SEMI | Specifier FunDec CompSt……
>
> Declarators：VarDec → ID | VarDec LB INT RB；FunDec → ID LP VarList RP | ID LP RP……
>
> Expressions：Exp → Exp ASSIGNOP Exp | Exp AND Exp | Exp OR Exp | … | ID LP Args RP | Exp LB Exp RB | Exp DOT ID | ID | INT | FLOAT……

他盯着屏幕，忽然笑了。

南大的 C— 是一份**课程实验文法**：有明确的评分标准、有 IR Simulator 虚拟机、有 QtSpim 目标代码执行、有老师提供的额外测试用例。学生按部就班，从词法分析写到目标代码，一门课下来，一个完整的编译器。

他的 Magel 语言是一份**自修文法**：没有评分标准、没有虚拟机的图形界面、没有老师给的测试用例，只有 `git log` 里深夜的提交、仓库里不断校准的专题文档、和屏幕另一头的 AI 搭档。他从 `pl0-super` 推到 `magel`，从四元式失败线退回来，从字符串缓冲的权宜之计改成堆上分配，从手动 `delete` 改成块作用域软释放。

方向竟然是一样的。

南大的同学在课程里被要求“手搓 C—”；他在住处自找麻烦“手搓 Magel”。一个在教室里，一个在住处；一个有老师点头，一个只有自己点头。

但两拨人干的事，本质上是一件事：**把一张地图从“老师画过的那半张”推到“自己能重算的整张”。**

他关掉书签，继续写 Magel 语言的对象表。

那天晚上他在提交信息里多写了一句：

> `// 南大的 C— 是课程，我的 Magel 是自找的。但地图是同一条。`

### 给生成器起名，比给语言起名还难

Magel 语言跑通之后，糖糖写了一个生成器，把 `.quad` 文件变成**自带虚拟机的独立可执行文件**。这个生成器现在叫 `magel/magel-emit`（原 `library/magel-emit`），它的名字也经历了一场小型命名危机。

他最初的灵感是 **C+-ava**——因为它是把 C 子集（C+-）变成可执行文件（-ava 听起来像 Java 的某种变体），简称 **cava**。

“cava 不错，”他自言自语，“简洁，好记，像咖啡。”

然后他停住了。

> “等等，这是 Magel 语言的工具。难道叫 **mcava**？
> 还是 **mc+-ava**？  
> 这符号也太多了，文件名里带加号减号，shell 里还得转义。”

他在 README 里打了几行草稿：

```text
magel-emit        # 现在叫这个（后来搬进 magel/）
cava                # 简洁，但不知道的以为是咖啡
mcava               # 有 Magel，但读起来像某个地名
mc+-ava             # 符号太多，文件名不友好
```

最后他叹了口气：

> “算了，还是叫 `magel-emit` 吧。
> 至少它诚实——它就是把 magel emit 出去。”

于是 `magel/magel-emit` 这个名字定了下来。它不短，不酷，但准确说明了自己的职责。

> **说人话旁白：**  
> 给工具起名就像给 Minecraft 里的宠物狼起名：  
> 你一开始想叫它“战神”，后来发现它只会坐在原地等你喂骨头。  
> 最后你叫它“狗子”。  
> `magel-emit` 就是那只狗子。

### 「字符串为什么不放在数据区？」

那天晚上他盯着 Magel 语言的类型表，第一句话就把自己问住了：

> 字符串的值是数据区里一串字节的基址。那 `a + b` 怎么办？数据区是**编译期布局**，运行期拼出来的串放哪儿？切片呢？`format` 出来的呢？

答案是有个静态缓冲——那是上一版的权宜之计：**下一次拼接会覆盖上一次的结果**。

所以他把手一摊：「别修缓冲了，**把字符串整个搬到堆上，运行时用 C++ 写**。」

那一天改完，字符串这件事就变成一句话：**值永远是堆地址，数据区只留只读字面量当复制源**。

> **规矩一：一条链只分配一次。**  
> `a + "x" + b + c` 摊平成**一次** `__vm_str_join`。两两接当然也能对，但中间那串没人拥有——没有哪个变量“是它”，于是没人释放，漏。表示一旦确定，优化就是顺手的事：把链摊平，只留一个结果串，它正好归被赋值的那个变量。

> **说人话旁白：**  
> 这就像 Minecraft 里合成物品：你不能先把木头合成木板、再把木板合成木棍、再把木棍合成剑——中间产物没人管，背包就满了。  
> 正确做法是一次性把配方摊平，直接出最终成品。

### 「谁负责还回去？」

堆上的东西总得有人还。糖糖选了**块作用域**：运行时数组与堆上的字符串，归**声明它的块**。出块、`break`、`continue`、`return`，按声明逆序还回去；`return` 出去的那个变量除外——它的所有权交给调用方。

> **规矩二：自动释放要能安全重入。**  
> 编译器插的释放是**软释放**：地址是 0、是数据区、或者已经还过，都当没这回事。理由很实在——显式 `delete a;` 之后变量还留着那个地址、块出口又要 drop 一次；两个变量指向同一块时多出来的一次 drop；这些都不该炸。程序中自己写的 `delete` 反过来是**严格**的。

> **说人话旁白：**  
> 这就像末影箱：你把东西放进去，出块的时候自动清空。但如果有人手动把东西扔了，末影箱不该报错——它应该当没看见。  
> 你自己手动扔的东西，那就得严格：扔错了、扔重了，都是你的问题。

`T mut&` 不动：**灵活指针是手动所有**，自己 `delete`。三档所有权写在 README 里，一句话一张表。

### 「大整数和容器放哪儿？」

`lang::BigInteger`（任意精度整数）与 `lang::List<T>` / `lang::Set<T>` / `lang::Map<K,V>` 三个容器进来的时候，糖糖遇到一个和「字符串」一模一样的抉择：**值放哪儿**。

> 放数据区？它们是**运行期**长大的，数据区是编译期布局。  
> 放堆、当字节串？那 `v.push` 就得在语言侧写逐字节的协议——和“字符串逐字节循环”一样脏。

于是有了**运行期对象表**：句柄 → C++ 对象。

后来这层接口也收口了：源码只写 `lang::List<T>`、`lang::Set<T>`、`lang::Map<K,V>`，早期的
`vec/set/map` 类型拼写直接删除；`__vm_vec_*` 只作为看不见的 VM ABI 留在底层。标准算法
也不再保留 Magel 包装文件：编译器识别 `std::algorithms`、检查泛型实参与回调签名，然后直接
调用胶水层。排序复制输入列表后使用带辅助缓冲区的自底向上稳定归并排序，时间复杂度为
$O(n\log n)$，并且不占用递归调用栈。

> **规矩三：句柄和地址要一眼分得开。**  
> 句柄取 `1e12` 起的**高位区间**——堆地址才几千、数据区地址更小，于是 `(free, …)` / `(drop, …)` 里就能分出“这是对象句柄还是内存地址”。省掉一整个“先问类型再决定”的分支。

> **说人话旁白：**  
> 就像 Minecraft 里，物品栏槽位编号从 0 开始，世界坐标是几万几万。  
> 你一眼就能看出“这是背包里的第几格”还是“这是地图上的哪个位置”。  
> 糖糖把这个直觉搬进了编译器：句柄和地址，一眼分开。

顺手把三件事钉死：

- **容器里的字符串按副本存**；
- **对象类类型是值语义**；
- **大整数是附加功能**。

### 「能不能把虚拟机搬进产物里？」

最后一件是糖糖一直想做、也一直没敢做的：**让产物自己带虚拟机**。

他一直记得第一章那个说法——「产物自包含」。但那是“不依赖生成器”，产物仍然要 `stackvm` 那个进程去跑 `.quad`。于是他拿 `library/template` 写了个生成器（现在是 `magel/magel-emit`）：

> 用模板把四元式、数据区字节、布局表**模板化成 C++ 常量**，再把 `library/stackvm` 与 `library/big_number` 的**源码整段内嵌**进同一个文件。`g++ -std=c++17 -O2` 一编——出来就是一个**独立可执行文件**：没有 `.quad`、没有 `.data`、不依赖本仓库、只 `#include` 标准库。

### 这一夜踩出来的坑（都是“表示”的账）

写到凌晨，他把这一轮的 bug 抄成一张单子，因为**每一个都不是新写的代码写错，而是旧地方的表示在新的用法下露出来的**：

```text
Heap::allocate     切块之后还抱着 blocks_[index] 的引用（vector 扩容就失效），

Node::storeAt      原来"先算地址再算值"，递归重入时地址临时量被内层覆盖
```

> **说人话旁白：**

## 第九章 今晚学到的道理（06:39）

写到天快亮的时候，把这几个月（尤其是今晚这几个小时）学到的东西记下来，免得忘：

1. **给一层抽象写第二份实现之前，先问它省了什么。**  
   四元式那条线不是做不出来，是“成本来自 IR、收益没兑现”。抽象要先证明收益，再谈优雅。

2. **“跑通”不等于“对”。**  
   三处优化器缺陷逼得好几个示例只能写 `# 优化: 否`——那是遮羞布，不是方案。能复现、能定位、能写进文档，才算处理完。

3. **表示选错，后面每一步都在还债。**  
   扁平化不是“差一点”，是**方向不对**。换表示比修一堆 bug 便宜。

4. **能重算的才是真懂。**  
   当年编译原理课没欠考试——老师只教了 LL(1)、LR(0)、四元式 DAG 图化简和词法分析的全部，考试分数他很高；但没教过的 SLR / LALR / LR(1) / IELR，他也没自己推过。这一次从 LL(0) 到 IELR，FIRST/FOLLOW 自己推、项集自己闭包、冲突一条条看，所以每一处消解都解释得出来——这才叫把那张地图补完。

5. **失败要复盘，而且要写清楚。**
   没做成的路线也能留下结论、复盘和可重放的工程证据。把它写下来，比把它藏起来值。

6. **编的只有壳，数字不能编。**  
   人名、机构、评审会都是虚构；命令、指令、模式、提交时间和可复现的验证结果，一个字都不能编。

7. **删掉的东西往往比留下的多。**  
   今晚删了两个子库、删了剧本的一大半、也删掉了“再上一层”的执念；留下的是一套能被别人重跑的四元式优化引擎，和一套一个人就能看完的 `pl0-super`。

8. **共用一张桌子，比分工更难。**  
   五个 agent 各改一档后端，代码都写得对，可它们抢的是同一棵工作树。结对靠默契，成队必须靠规矩——编译上锁、提交按路径、验收先跑秒级那档。

9. **值放在哪儿，语言就长什么样。**  
   字符串搬上堆，“拼接摊平”才有意义；`lang::BigInteger` / 容器做成对象句柄，“句柄与地址一眼分开”就省掉一整个分支；对象定成值语义，“别名悬挂”从源头上就没有；虚拟机源码能整段内嵌进产物，“自包含”才真的成立。先想清楚值放哪儿，再写第一行代码。

10. **地图外面不止你一个人。**  
    南大的同学在课程里手搓 C—，你在住处自找麻烦手搓 Magel。方向撞上了，不是竞争，是安慰。**原来这条路上，还有别人。**

06:39，楼下早餐铺该开了。把这些存进仓库，然后去睡。

## 第十章 让产物自己会画图

后半夜两点，糖糖推门进来的时候，屏幕上并排开着两张图：左边一张是 LALR(1) 档的语法树，右边一张是 GLR 档的语法图——左边 GSS 的节点里有一个是金色的，下面并排躺着两棵结果树。

「这什么？」

「这个文法是二义的。」我说，「`if cond then if cond then other else other`——那个 `else` 到底归里层还是外层，两种读法都成立。GLR 不挑，它两边一起走，走完把两条都摆出来给你看。」

「金色那个呢？」

「被运行时接受的节点。图上每一层是「一个状态 + 一个节点号」，边上是符号——实线是移进，虚线是归约，虚线后面那个 `·P2` 是产生式号。」

「那左边这张呢？」

「LALR(1) 档的语法树：框里第一行符号名，第二行词素，叶子和分支两个底色。两张图都是产物**自己画的 SVG**——不放图床、不装第三方库，只用标准库拼字符串；同一棵树每次画出来的坐标一模一样，所以能进 `expected` 做逐字节比对。」

「为什么只给这几档？」

「语法树绘图给 `lalr` / `lr1` / `ielr`——这三档共用同一套 LR 运行时，`%tree` 之外也能用 `parse_tree()` 单独建一棵树来画。语法图给 `glr`：它有 GSS 可画，还有一批结果树可以并排摆。别的模式产物里连这些方法都不发——**生成期就决定**，不留运行时开关。

演示程序多认两个开关：`--svg tree.svg` / `--dot tree.dot`。不给开关的时候，输出与从前一个字节都不差。」

「那两种模式呢？一个 GLR，一个……那个 `dd`？」

「`dd` 是递归下降，第十四种模式。它跟前面十三种都不一样：**不建表**。每个非终结符一段『按产生式声明顺序逐条试』的逻辑，试失败就把词法器的位置、Token 下标、行列号一起退回去，再试下一条。听起来笨，但它有个好处——取法完全由你写产生式的顺序决定。」

「有代价吧。」

「三个：不能有左递归（生成期直接报错，还告诉你把 `expr := expr PLUS term` 改写成右递归）；歧义文法只保留**第 1 条匹配路径**，不像 GLR 那样全列出来；回溯最坏是指数级，所以把最可能命中的产生式写在前面。六档全支持，`%sync` 也照旧能用。」

「GLR 是加回来的？」

「第三十一段的时候跟 Java 一起删过。这次照同一份清单加回来：C++17 / Python / Rust / Go 四档，GSS 运行时 + 冲突候选表；结果用各档自己的动态容器保存。」

天亮前我们干了第三件事：**把人写死的产物文案搬进模板**。

`RESULT.md` 里那十一节说明（容量宏、%sync、%commit、IELR 拆分、展望项、Mermaid 图示……）早就写好了模板、一直没接线，C++ 那边还在用 `out += "字面量"` 拼。我把它们全接上：生成器只负责摆数据，小节出现不出现由模板里的条件判断说了算。改完生成 135 组产物逐字节比——**0 差异**。

「那 `mermaid.cpp` 呢？」

「一视同仁。图的源码、HTML 页面骨架、CSS、导语、两张表、连『动作：移进 a b』这种摘要句都是模板，一共 20 份；`joinLines` / `joinTexts` 两个拼接助手删掉了。两轮加起来 135 组产物还是 0 差异。」

「一个字节都没动，那图什么？」

「图下一个改文案的人不用碰 C++。」我说，「也图我这种半夜三点改文案的人，不用重新读一遍 4000 行的 `project.cpp`。」

## 第十一章 Rust 的库函数：从“给 C 写的”到“用 Rust 自己的”

Rust 后端加回来之后，词法那一关先过了——`%token regex` 不再走生成器自带的 DFA 表，原样交给官方的 `regex` crate，产物里的 `Dfa` 常量整套删掉，三张表在第一次取 Token 时各编译一遍。

但词法只是门口。真正进门之后，糖糖才发现：**Rust 那一档的运行时，从第一天起就是“用 Rust 语法写 C”。**

```rust
// 这不是 Rust，这是穿着 Rust 外衣的 C
pub struct Parser { /* ... */ }
impl Parser {
    pub fn run(&mut self, text: &str) -> bool { /* ... */ }
    pub fn result(&self) -> i32 { /* ... */ }
}
```

「你看这个 `bool`。」他把屏幕转过去，「C 那套是『`bool` 返回 + `Error &` 出参』，我顺手就搬过来了。Rust 有 `Result`，为什么不用？」

屏幕另一头沉默了一会儿，回了一句：「因为搬过来最快。」

「那现在不快了。」

### 第一个照面：`%destructor` 被生成期直接拒绝

Rust 后端刚加回来的时候，`%destructor` 是照 C 那套写的：错误恢复弹栈时，按「栈上那个符号绑的是哪个成员」调对应的清理片段。

可 Rust 有 `Drop`。

```rust
// C 的写法：手动登记清理片段
%destructor <str> { free($$); }

// Rust 的写法：Drop 自动跑，不需要你登记
impl Drop for StrValue {
    fn drop(&mut self) { /* ... */ }
}
```

于是生成器在 Rust 档下遇到 `%destructor` 就直接拒绝，报一句：

```text
错误：Rust 产物不支持 %destructor——语义值按值拷贝，生命周期由 Drop 负责。
      如果你需要手动释放，请在 %class_body 里自己实现 Drop。
```

这条报错后来写进了 `14-languages-and-products.md`：Rust 与 Go 两档都不支持 `%destructor`，理由一句话——**目标语言自己有所有权，不需要生成器替它管。**

> **说人话旁白：**  
> C 里你借了东西要自己还，Rust 里你借了东西编译器盯着你还。  
> 你把 C 的「手动登记清理」搬到 Rust，就像在 Minecraft 里造了一个红石自动门，  
> 结果发现那扇门本来就是自动的——你只是多摆了一堆红石。

### 第二个照面：语义值按值拷贝

C 的 `%union` 是一块共享内存，哪个成员是活的靠你自己记。Rust 没有 `union` 那套（有 `union`，但 `unsafe`），糖糖一开始想用 `enum` 硬套：

```rust
enum ParserValue {
    Ival(i32),
    Fval(f64),
    Sval(String),
}
```

但生成器要的是「按符号分成员」——`%token <ival> NUMBER` 和 `%token <sval> ID` 对应不同的动作展开。`enum` 能表达，可生成器得知道每个符号绑的是哪个 variant。

于是他换了个更直接的做法：**语义值按值拷贝，每个符号一个字段。**

```rust
pub struct ParserValue {
    pub ival: i32,
    pub fval: f64,
    pub sval: String,
}
```

所有符号共用这个结构体，动作里 `$1` 展开成 `values[1].ival`，和 C 的 `%union` 写法长得一样，但底层是 Rust 的按值拷贝。代价是每个值都复制整个结构体——语义值小的时候无所谓，大了就浪费。

「你为什么不直接上泛型？」屏幕另一头问。

「泛型要改所有动作的翻译，」他敲了一行，「而且 Rust 的泛型在生成器里展开，报错会指到生成器，不是 `.gram`。我不想要那种报错。」

「那 `%union` 呢？」

「Rust 档下 `%union` 照 C 的成员声明写，但生成的是结构体，不是联合体。动作里 `$1 + $3` 还是展开成 `values[1].ival + values[3].ival`，和 C 产物逐字一致——只不过 Rust 那边是 `i32`，C 那边是 `int`。」

后来这条写进了 README 的实测覆盖表：Rust 只列语言中立的文法，`union_demo.gram` 这类 C 文法不适用——因为 `%union` 的成员要写成 Rust 字段。

### 第三个照面：错误处理从 `bool` 改成 `Result`

C 那套是「`bool` 返回 + `Error &` 出参」，生成器不开异常，错误一路往上传。Rust 有 `Result<T, E>`，糖糖本来想直接换：

```rust
pub fn run(&mut self, text: &str) -> Result<(), ParseError> {
    // ...
}
```

但问题来了：**产物里的错误消息要和 C / C++17 / Python / C# / Go 逐字一致。**

C 那边错误码是 `-26` / `-27`，消息是「第 N 行第 M 列：期望 A / B 之一，实际是 C」。Rust 如果换成 `Result`，错误类型就得带上这些字段：

```rust
pub struct ParseError {
    pub code: i32,
    pub line: usize,
    pub column: usize,
    pub message: String,
}
```

然后 `main.rs` 里：

```rust
match parser.run(&input) {
    Ok(()) => println!("{}", parser.result()),
    Err(e) => eprintln!("错误：{}", e.message),
}
```

这本来没问题。但生成器里 C 那套错误处理是「`bool` 返回 + `Error &` 出参」，翻译到 Rust 要写两套模板：一套给 C / C++17 / Python / C# / Go（`bool` + 出参），一套给 Rust（`Result`）。

「值得吗？」他问自己。

「不值得。」他回答自己，「但 `Result` 是 Rust 的库函数，不用它，Rust 那一档就永远是『用 Rust 语法写 C』。」

于是他写了第二套模板。生成器里多了一个 `code_gen_rust.cpp`，里面有一半代码在干一件事：**把 C 那套 `bool` + 出参翻译成 Rust 的 `Result`。**

> **说人话旁白：**  
> 这就像 Minecraft 里你本来用木镐挖石头，挖得动，但慢。  
> 后来你换了铁镐，快了一倍，但你得重新学一遍怎么挖。  
> 糖糖换 `Result` 就是这样——快是快了，但生成器里多了一套翻译。

### 写 Rust 版库：从「照搬」到「按 Rust 的方式重写」

Rust 后端稳定之后，糖糖开始把 `library/` 下的几个 C++ 库往 Rust 搬：

| C++ 版 | Rust 版 | 说明 |
| --- | --- | --- |
| `library/transfer` | `library/transfer-rust` | 四元式后端：两版共同覆盖 MIPS / 8086 / ARM → 模拟执行；C++ 版另有 Hydra86 原生汇编与嵌入执行，Rust 版是独立零依赖 crate `quad_transfer`；26 份 Rust 示例 23 通过 / 0 失败 / 3 跳过 |
| `library/preprocess` | `library/preprocess-rust` | 通用预处理器：`#` / `%` 指令、条件编译、include / import；独立 crate `preprocess`，零依赖；56 组 CLI 参数的产物 / stdout / stderr / 退出码与 C++ 版逐字节一致 |
| `library/json` | `library/json-rust` | JSON 库：解析 / 序列化 / 路径查询 / 模型投射；独立 crate `json`，只用标准库、零依赖；91 条语料 + 25 条命令，与 C++ 版实质差异 0 |

搬的过程不是「把 C++ 逐行翻译成 Rust」，而是「**用 Rust 的库函数重新实现一遍**」。

比如 `preprocess-rust` 里的字节下标。C++ 版用 `std::string_view`，下标是 `size_t`；Rust 版用 `&[u8]`，下标是 `usize`。看起来一样，但 C++ 的 `string_view` 可以指向任意内存，Rust 的 `&[u8]` 有生命周期。于是糖糖在 Rust 版里加了一层「按字节工作的下标约定」，写进了技术报告：

```rust
// C++ 版：string_view 可以直接切
std::string_view token = text.substr(pos, len);

// Rust 版：&[u8] 切片，生命周期跟着 text 走
let token = &text[pos..pos + len];
```

又比如 `json-rust` 里的模型投射。C++ 版用模板特化，Rust 版用 trait：

```rust
// C++ 版：模板特化
template<> struct JsonModel<MyStruct> { /* ... */ };

// Rust 版：trait 实现
impl JsonModel for MyStruct { /* ... */ }
```

「你为什么不直接用 `serde`？」屏幕另一头问。

「因为 `serde` 是第三方依赖。」他敲了一行，「这个库的定位是『只用标准库、零依赖』，和 `json-rust` 的 README 写的一样。」

「那 Rust 后端为什么用 `regex` crate？」

「因为 `regex` 是 Rust 官方的，不算第三方。」他停了一下，「而且词法正则那件事，自己写 DFA 表真的不如用官方的。」

### 踩坑记录：C++ → Rust 的类型映射

搬到凌晨，他把这一轮的坑抄成一张单子：

```text
C++ size_t → Rust usize     下标类型对了，但溢出行为不同：
                            C++ 无符号溢出是环绕，Rust debug 下 panic
C++ string_view → Rust &str 生命周期要显式标注，不能像 C++ 那样随手切
C++ bool + Error & → Rust Result<T, E>
                            错误码要带进 E，不能像 C 那样直接返回 false
C++ 模板特化 → Rust trait    trait 实现要写在类型定义旁边，不能散落
C++ 异常 → Rust panic       生成器不开异常，Rust 版也不 panic，统一 Result
```

> 糖糖在单子最后写了一句：**这一轮没有一行是「算法」的活，全是「库函数」的活。**  
> ——和第三章、第八章合起来看，这条线其实一直在讲同一件事：**表示选错，后面每一步都在还债；库函数选错，后面每一步都在翻译。**

> **说人话旁白：**  
> 这就像 Minecraft 里你从主世界搬到下界：  
> 主世界的方块在下界不能直接用，你得重新合成。  
> 糖糖这一轮，就是在给 Rust 重新合成一套库函数。

### 本章补记

第七章讲的是「换一台引擎」——把词法正则从自带 DFA 换成官方 `regex` crate。这一章讲的是「换一套库函数」——把运行时从「用 Rust 语法写 C」换成「用 Rust 自己的库函数」。

两件事合起来，Rust 那一档才算真正落地：

- 词法用 `regex` crate，不再背 DFA 表；
- 错误处理用 `Result<T, E>`，不再用 `bool` + 出参；
- 语义值按值拷贝，`%destructor` 被生成期拒绝，生命周期交给 `Drop`；
- 三个库（`transfer-rust` / `preprocess-rust` / `json-rust`）全部零依赖，只用标准库。

后续开发继续沿用同一条验收原则：先生成，再用目标工具链编译，最后运行并比较期望输出。

### 关于「库函数」的最终结论

后来有人问糖糖：「你为什么非得把 C++ 库搬成 Rust 版？直接用 C++ 版不就行了？」

他说：「因为 Rust 那一档的产物是给 Rust 用户看的。如果产物里的运行时是『用 Rust 语法写 C』，那用户为什么要用 Rust？」

> 「C 的库函数是工具，Rust 的库函数是语言的一部分。  
> 你用 C 的方式写 Rust，Rust 不会报错，但 Rust 用户看得出来。  
> 就像你在 Minecraft 里用木镐挖钻石——挖得到，但所有人都知道你该换铁镐。」

对方听完，沉默了一会儿，说：「那你现在换了吗？」

糖糖说：「换了。`regex`、`Result`、`Drop`、`&[u8]`、`trait`——全换了。」

—— 第十一章 · 完

## 第十二章 GPT 的延续

第十一章写到 Rust 换库函数时，本来已经很像一个句号。

生成器有六档语言，模板归位，GLR 加回来了，Rust 也不再像“披着 Rust 语法的 C”。故事可以停在这里：一个人，两三个 AI 搭档，一张从课堂边界外面补回来的地图。

但后来糖糖又开了一轮。

这一次不是加语言，也不是再搬库，而是去碰一个更像 IDE 里的问题：**文本改了一小块，解析器能不能少重跑一点？**

最先做的是保守的：DD 和 LL 只缓存同文本结果，文本变了就重算。听起来朴素，但接口先立住了：C++17 和 Rust 都有 `IncrementalCache`，调用方不用猜将来 API 会不会换。

接着是确定性 LR。LR 的栈太容易牵一发动全身，糖糖没有一口气做“完整增量解析”，而是先做了增量友好的版本：token cache、前缀状态 checkpoint、每 N 个 token 存一次栈快照。文本变化后，从公共前缀里最近的 checkpoint 恢复，而不是从头解析。

真正绕的，是 GLR。

GLR 不只有一条栈，它有 GSS；不只有一个结果，它可能有一片 forest。缓存 AST 没用，缓存一棵树也不够，因为二义文法里同一个跨度可以有多个归约候选。于是缓存对象换成了 packed forest：节点有稳定 ID，候选记录产生式和孩子，节点反向保存 parents。

文本一变，先失效直接覆盖的 token span，再沿 parents 往上传递，把所有受影响祖先一起标脏。没碰到的节点保留 ID；插入或删除后，后缀跨度整体重映射；重新跑出来的候选再和旧 forest 对齐，能复用的复用，过期的删掉，不可达的也清掉。

这还不是完整 GLR 增量解析。GSS 控制流程仍然重跑，Earley / CYK 的图表判定也仍然重建；语义动作默认不复用，只有调用方显式声明 `Pure` 且语义环境版本一致，才允许同文本成功结果复用。CST 原位修补、GSS checkpoint、语义动作副作用隔离，这些都还在后面。

但这轮把门打开了。

> 以前的 ParseEngine 是“能生成解析器”。
> 后来的 ParseEngine 开始回答另一个问题：
> **如果解析器活在编辑器里，它怎么记住上一秒发生过什么？**

写到这里，标题里的“满级”终于换了一层意思。

不是功能满了，而是路线变了：从“把所有模式都生成出来”，走到“让生成出来的东西能在持续变化的文本里活下去”。

## 第十三章 把后端接进一台真的 8086 风格虚拟机

`library/transfer` 原来已经有一档 8086 教学后端。

它会把四元式降成带 `AX`、`DX`、`MOV`、`IDIV` 的教学汇编，再交给库内模拟器执行。用来讲固定寄存器对、乘除法和内存操作很合适，但它终究是一台为课程模型服务的机器：指令、配置和运行时都由 `transfer` 自己解释。

后来仓库里多了一台 Hydra86。它也是 8086 风格，却不是那档教学模拟器的另一个名字。它有自己的 `.data` / `.code` 汇编格式、函数调用、标签规则、系统调用、汇编器和 VM；**它自己就是仓库里的一个独立工程**，能单独汇编、执行、反汇编和调试，手册与来历都在它那个独立仓库里。要对接它，不能把原来的 8086 文本做字符串替换；必须从统一 IR 再做一次真正的 lowering。

糖糖给 `t1t transfer` 加了第四个目标：

```text
t1t transfer demo.quad --target=hydra86 --asm
```

这一档把不超过 64 位的整数标量、算术与位运算、比较、控制流、函数调用、递归、有符号除法和整数输出降成 Hydra86 原生汇编。浮点、字符串、向量、文件和输入指令没有偷偷糊弄过去，不支持就生成期报错。

真正麻烦的不是“多写一个 switch”，而是把两个仓库边界接稳。`transfer` 的 Makefile 仍然可以零依赖地产生汇编；CMake 若按可配置路径（`T1T_HYDRA86_ROOT`，指向 Hydra86 独立仓库）找到源码，就链接稳定接口 `pvm_cli`，由 `Hydra86::runAssembly` 在同一进程里完成装配和执行。找不到 Hydra86 时，汇编生成仍然可用，只是不假装已经运行。

验收也不只看汇编长得像不像：直线算术、循环、递归和负数除法都进了测试，嵌入构建的 CTest 是 **9 / 9**。更硬的一条证据来自后面的 C-- 实验：前端实际生成的四元式被降成 **85 行 Hydra86 汇编**，VM 跑了 **140 个周期**，退出码 `0`，输出 `5`。

这一次，箭头终于不是文档里的虚线：

```text
严格 C-- → ParseEngine 前端 → 四元式 → transfer → Hydra86 汇编 → 汇编器 → VM
```

## 第十四章 秒杀严格 C-- 五次实验报告

“秒杀”不是把答案贴进 Markdown，也不是拿一个 C-- 超集假装完成课程要求。

真正省时间的，是前面四十一段已经把工具链铺好了。解析器生成器、四元式后端、数据流、SSA、寄存器分配、MIPS 模拟器和 Hydra86 接口都在仓库里；这一轮要做的是把它们收束到南京大学五次实验的边界里，并让每一句报告都能回到源码和运行结果。

第一步是守住语言边界。前端只认 `source/frontend/cminus.gram` 定义的严格 C--：`int`、`float`、数组、结构体、函数和控制流按实验文法进入；`for`、指针、`switch`、容器、接口这些超集语法必须拒绝。词法器和 LALR 解析器由 ParseEngine 实际生成，不是手写一个“差不多能过样例”的 parser。

第二步是把五份报告逐层接到同一份实现：

1. 词法与语法分析：Token、LALR 文法、AST 和错误定位；
2. 语义分析：符号表、作用域、类型推导和错误分类；
3. 中间代码生成：AST 到四元式、控制流、调用与返回；
4. 目标代码生成：基本块、MIPS 生成与模拟，再接 Hydra86；
5. 代码优化：数据流、SSA、局部与全局优化、执行前后对照。

原文档里的目录、页码标题、习题和答案被清掉；留下的是实验指导、完成报告、源码、实验框架、平台手册、提交要求和 C-- 文法附录。公式用 LaTeX，流程与结构图用 Mermaid，指令序列进代码块。报告不再像 PDF 逐页抄出来，而像一个能在电脑上继续维护的工程。

最后是一键证据链。`project/lab_report_nju/run-evidence.ps1` 会重新生成并编译严格 C-- 前端，跑 **4 个合法样例 + 4 个拒绝样例**，再构建后端、执行 **8 项测试**，把前端实产四元式送进完整流水线，并比较优化前后的 MIPS 结果。实验四再用仓库主线的 `library/transfer` 接 Hydra86，证明目标代码不是从手写四元式凭空来的。

所以“秒杀”的真正意思是：五份报告可以写得快，但每一份都背着同一条可重放的证据链。不是答案变简单了，是仓库终于积累到能把题目变成一次构建。

## 第十五章 把 Java 接回来，再给 JavaScript 一副 TypeScript 骨架

Java 曾经被删得很彻底。不是因为语法难写，而是完整后端要背语义动作、错误恢复、巨大分析表和词法 DFA；这些东西塞进 Java 类初始化代码，很容易撞上常量池或方法大小边界。那时继续维护一套“看起来齐全、规模一大就危险”的后端，不如删掉。

第 43 段没有假装把旧后端原样复活。糖糖先划了一条窄边界：只做两种最能体现运行时差异的模式。

- DD 把产生式按声明顺序分组，失败时恢复 Token 位置，再尝试下一条；
- Earley 直接实现 predictor、scanner、completer，能处理左递归与空产生式，歧义时先保留第一棵派生树；
- Java 产物是一份自包含的 `Parser.java`，词法正则交给标准库 `Pattern`；
- JS 产物叫 `parser.ts`，保留 `string`、`number`、联合类型和泛型容器等可擦除 TypeScript 标注，Node.js 22+ 可以直接运行。

“窄”也写进了生成期检查：语义动作、`%union`、`%sync`、`%commit`、`%copy` 和用户代码段不静默忽略，遇到就明确拒绝。在第 43 段当时，Java / JS 也不冒充 LL、LR、GLR 或 CYK 后端；模式不在 DD / Earley 里，同样直接报错。

这一轮最重要的不是多了两个语言名字，而是没有再生成 C-- 的超集式假产物。前端仍由 ParseEngine 读取 `.gram`、执行 DD 左递归检查或 Earley 图表构造，后端只把分析后的符号、产生式与词法规则摆进模板。Java 与 JS 共用 `code_gen_narrow.cpp` 的数据模型，但运行时分别写成两门语言自己的代码。

验收用了四个真实生成工程：`dd_expr` 与 `chart_nullable` 各生成 Java、JS 一份。Java 22 编译运行通过；Node.js 26 对带类型标注的 `parser.ts` 做语法检查并直接运行；四份输出与仓库原有 `.expected` 一致。另加一份“同一非终结符分散声明”的 DD 文法，确认重新分组后仍按声明顺序回溯。

后续维护又把 CYK 接进这条窄后端：CNF 跨度表负责判定，命中后用原文法 Earley 表
恢复第一棵树，所以输出不会混入合成 CNF 节点。Java 22 与 Node.js 26 已覆盖歧义、
可空/左递归、空输入和非法输入。

## 第十六章 把最后两格补上，再把记忆收回仓库

地图上还剩两个看起来很小的缺口。

Go 已经有 GLR 的图结构栈，却没有 Earley 和 CYK；`--lang gram` 明明不生成运行时，
也被同一条“目标语言不支持 GLR 家族”的检查挡在门外。前一个缺口是运行时，后一个缺口
只是边界写错了，但它们在支持矩阵里都表现成同一个词：**不支持**。

糖糖没有给 Go 再写一套结果树。他把工作拆成两层：Earley / CYK 负责回答“这串 Token
能不能接受”，既有 GSS 负责回答“原文法有几种解释、每种解释的语义动作算出什么”。
CYK 的 CNF 合成节点只活在判定表里，不进入用户看到的树。这样 `2 + 3 * 4` 仍然会留下
`14` 和 `20` 两个结果，而不是只剩一句“接受”。

`gram` 那一档反而更简单。它没有栈、没有语义动作运行时，也没有内存释放问题；它只要
原文、分析报告和 `RESULT.md`。于是生成期的 GLR / Earley / CYK 运行时限制对它全部绕开，
十六种模式都能导出。这里最重要的不是“多放行三个字符串”，而是把规则说清：
**不生成运行时的档，不该被运行时能力检查拒绝。**

验收时还闹了一个很像真 bug 的笑话。第一版脚本拿 `chart_nullable.gram` 去逐档验证
十六种模式，跑到 LL(0) 立刻失败。问题不在导出，而在那份文法本来就有可空、左递归和
歧义，天生不可能满足 LL(0)。换成能过最严格条件的 `ll0_demo.gram` 后，十六档各自产出
`.gram`、分析报告和 `RESULT.md`。这件事后来被写进交接单：**测试输入也有前置条件，
别把“样例不适合算法”误判成“功能没有实现”。**

接着，Java / JS 的 CYK 也沿同一条思路补上。两档没有 GSS，就让 CYK 做 CNF 跨度判定，
命中后用已经存在的 Earley 原文法表恢复第一棵树。它们仍然诚实地保持窄后端边界：
不执行语义动作，不冒充错误恢复，不因为多了 CYK 就声称支持全部十六种模式。Java 22
和 Node.js 26 真正编译、检查并运行了歧义、空输入、左递归和非法输入，不是只看生成器
退出码为零。

功能补完后，仓库里又出现了另一种重复：`AGENTS.md` 有当前交接规则，独立会话记忆目录里
也有一套长期笔记。后者记录过很多真实事故，但也保存着“六种语言、十二种模式、Java
坚决不加、306 份模板”这类当时正确、现在错误的快照。新会话一旦先读到旧数字，就会把
历史重新写回现在。

最后一次清理没有删经验，只删了第二个真相源。路径转换、编译锁、LSP 单一语义源、成对
Rust 库、Markdown 表格、Mermaid、预览图视觉检查，以及这轮图表模式的十二条开发经验，
全部归并进 `AGENTS.md`；独立会话记忆目录和忽略规则一起删除。从此仓库只保留一份能接手
的交接单：新结论写进对应章节，事故写清触发条件、修复方法和防复发检查。

变化的是地图和交接方式：Go 与 `gram` 都到十六种模式，Java / JS 各有三种窄模式，
384 份模板、155 个实测语言组合，而维护经验不再散落在仓库外缘。

## 第十七章 给虚拟机装一扇门

Magel 已经会算大整数，会拼字符串，会开文件，也会把 `lang::List`、`lang::Set` 和 `lang::Map` 放进运行期
对象表。每增加一种能力，最直接的办法都是去 StackVM 那张内置函数表里再添一项。最初这
很方便，后来却越来越像在墙上凿洞：数学库能进去，容器能进去，下一块开发板的串口、传感器
和 C++ 业务对象难道也要逐个焊进虚拟机？

真正缺的不是又一个内置函数，而是一扇有门框的门。

门的外侧是宿主 C++，里面是 Magel 与 StackVM；门框就是 ABI。第 44 段先在 VM 层加入
`NativeRegistry` 与 `NativeCallContext`。宿主函数按名字注册，参数和返回值只经过整数槽或
浮点槽；字符串和内存不把内部容器裸露出去，而是通过上下文受控读取、分配和报错。这样，
应用可以换，VM 不必跟着改。

```mermaid
flowchart LR
    Magel["Magel 宿主声明"] --> TYPE["类型检查 / 泛型单态化"]
    TYPE --> CALL["call 稳定符号"]
    CALL --> BIN[".quad 或 .svmb"]
    BIN --> VM["StackVM"]
    REG["C++ NativeRegistry"] --> VM
    VM --> CPP["宿主函数 / 设备 / 业务对象"]
```

Magel 一侧只负责把门牌写清楚：

```c
type HostHandle<T> = uint64;
impl uint64 : ExplicitConvert<HostHandle<int32>> = counter_from_uint;
impl HostHandle<int32> : ExplicitConvert<uint64> = counter_to_uint;
HostHandle<int32> cpp_add(HostHandle<int32> a, HostHandle<int32> b);
T cpp_identity<T>(T value);
```

`type Name = ABI;` 声明名义宿主类型。一个 `HostHandle<int32>` 即使底层用 `uint64` 承载，也不会因此
偷偷获得整数加减；复杂 C++ 对象只把句柄或指针送过边界，不复制宿主布局。转换接口
明确写出哪些转换被允许；无函数体、以分号结束的函数只登记宿主签名，不伪造一份 Magel 函数体。重载冲突、重复
转换、缺失转换和运行时漏绑定，都在各自该报错的层次停下来。

门的另一侧不用手拆每一个槽：

```cpp
struct CounterTag;
using Counter = magel_glue::Handle<CounterTag>;
magel_glue::Registry glue;
glue.bindTypedImplementation<Counter, uint64_t>("counter_from_uint", from_uint);
glue.bindTypedImplementation<uint64_t, Counter>("counter_to_uint", to_uint);
glue.bindTyped<Counter, Counter, Counter>("cpp_add", add);
glue.bindTypedGeneric<int32_t, int32_t>(
    "cpp_identity", {"int32"}, identity);
glue.install();
```

`Codec<T>` 负责 bool、定宽整数、浮点、`std::string` 与 `Handle<Tag, Rep>` 的边界转换；应用
也能为自己的平凡 ABI 类型补特化。泛型没有被偷换成运行期猜类型：已有预处理器仍在编译期
单态化，`bindGeneric` / `bindTypedGeneric` 只按同一规则登记稳定的特化符号。

这里还有一条故意留下的限制：函数地址不能写进 `.svmb`。地址只在当前进程有意义，把它
序列化既不可移植，也会把程序文件和某次宿主构建绑死。因此 `.svmb` 保存调用符号，加载后
由当前宿主重新挂同名注册表。`magel-emit` 的 C++ 两档通过 `--glue app.cpp` 在生成期把应用
注册代码原样内嵌；Rust 档不提供应用胶水层。少一点“自动”，换来的是同一份程序可以进入不同宿主。

当时的验收分两层：StackVM 通过 **210 项断言**，其中包含程序保存为 `.svmb`、重新加载、重挂
注册表再执行；Magel 通过 **52 个正常样例 + 80 个错误样例**，覆盖宿主泛型、字符串、
显式转换、漏绑定、重载冲突与非法宿主算术。代码分成两个提交：通用 VM 注册表一段，
Magel 类型化胶水一段，工作区收尾保持干净。

以前，Magel 能调用的是“虚拟机替它准备好的世界”。现在，门终于打开了：语言仍然检查类型，
二进制仍然只认稳定符号，而门外可以是一段普通 C++，也可以是一台真正的设备。

## 第十八章 当 Magel 不再只是 C 的影子

后来，Magel 的定位终于改清楚了：它不是“C 的一个子集”，而是一门面向 StackVM 的
C 风格语言。语法看起来熟悉，但类型、生命周期、模块和运行时边界都由虚拟机自己的规则
决定。这个改名不是文案修饰，而是后面一串设计能够同时成立的前提。

首先统一的是接口协议。自由的 `operator+` 被禁止，所有扩展行为都通过 `I` 前缀接口登记：

```c
struct Money : Add<Money, Money>, Drop {
    int cents;

    Money(int value) { self.cents = value; }
    Money leftAdd(Money other) {
        Money result = new(self.cents + other.cents);
        return result;
    }
    void drop() { }
};
```

`Add` / `RightAdd` 区分运算方向，`ExplicitConvert` / `ImplicitConvert` 管转换，
`Index` 和 `Iterator` 管索引与迭代。结构体能实现它们，带载荷的泛型枚举也能：

```c
enum Choice<T> : Add<Choice<T>, Choice<T>> {
    None, Value(T value);

    Choice<T> leftAdd(Choice<T> other) { return other; }
    int kind() { return 7; }
};
```

枚举因此不再只是“标签 + 载荷”的被动数据。它可以有方法，可以实现普通接口，也可以通过
接口参与运算符重载；泛型载荷仍在编译期单态化，模式匹配继续负责安全解构。

生命周期也从“分配一块、记得 delete”往前走了一步。结构体内部允许静态字段和静态方法，
同名方法是构造函数，`new(args)` 根据左侧类型调用它。析构不再借用 `delete` 这个词：
实现 `Drop.drop()` 的值对象离开作用域时自动析构，也可以用 `drop value;` 提前调用；
`delete` 只做裸堆释放。这个边界让资源清理和内存释放终于不再混成一件事。

然后是协程。标准库把无参 `void` 函数指针当成任务，`create` 返回名义类型句柄，普通整数
不能冒充它：

```c
lang::SharedCoroutineHandle task = lang::SharedCoroutine::create(worker);
lang::SharedCoroutine::wait(task);
```

`yield` 会保存当前 PC、求值栈、调用帧和待绑定参数，再切到下一个可运行上下文；协程根函数
返回时，等待它的上下文会被唤醒。C++ 与 Rust 两套 StackVM 使用相同的状态模型，
`RunResult.coroutines` 会留下每个上下文最终的状态、PC、帧深度和等待关系。

嵌入式宿主还需要知道 VM 正在做什么。于是机器新增了两类不写死平台的回调：宿主提供
单调纳秒时钟，VM 记录精确起止时间与耗时；宿主设置间隔 N，VM 每完成 N 条指令触发一次
钩子，报告累计指令数、实际执行的 PC、协程句柄和操作码。时钟来源由宿主决定，桌面端可用
高精度单调时钟，开发板也可以接自己的硬件计数器。

模块 API 默认显式导出。普通函数天然是模块 API；实现细节写成 `inline`，
同模块照常调用，别的模块即使写出完整限定名也会在编译期被拦住。这里的 `inline` 不是
性能暗示，而是可见性。`.svmb` 随之升级到 v3，把公开入口单独写进 exports 表；内部标签
继续留在程序中供实现调用，却不再冒充可链接 API。宿主函数则由无函数体的签名自动识别，
源码不再显示 `extern`。后来又升到 **v4**：在 exports 之后追加一节**调试信息**
（指令下标 → 源码位置），于是 VM 能报出"运行到哪一行、在哪一行出错"，并把调用栈翻成源码级；
`magel-emit` 导出的独立程序同样带着这张表。位置里的语言源码字段（`.mgl` 文件与行号）留好了槽位，
但组装期只拿得到四元式行，所以目前显示的是 `.quad` 行号。

这批能力最后不是靠“能生成”收尾，而是靠三组回归闭环：Magel **70 个正常样例 +
105 个错误样例**，C++ StackVM **234 项断言**，Rust StackVM **12 项测试**。其中包含
协程交错执行、句柄类型拒绝、枚举运算符接口、构造与自动析构，以及精确时钟和每 N 条
指令钩子的确定性测试。

到这里，Magel 已经很难再被叫作 C 的子集。它借了 C 的外形，但模块、泛型枚举、接口协议、
值生命周期、宿主胶水、二进制程序和协程上下文，都在为一台可嵌入的虚拟机服务。

## 第十九章 标准库不该知道宿主长什么样

容器、文件和协程落地以后，标准库还缺四块常用能力：把文本变成值、生成随机数、整理路径，
以及观察和批量使用 VM 内存。它们看起来都不大，却很容易越过语言与宿主的边界。

解析先统一错误模型。`std::parse::Parse` 不返回哨兵值，也不靠异常，而是把空串、非法文本和溢出
区分成 `std::parse::ParseError`，所有入口都返回 `Result<T, ParseError>`：

```c
Result<int64, std::parse::ParseError> value = std::parse::Parse::parseInt64("-42");
Result<float64, std::parse::ParseError> real = std::parse::Parse::parseFloat64("12.5");
```

这里最终采用 `Result`，不是旧名字 `Result`。它和 `Option` 一样是标准库泛型枚举，`?`
只在错误类型一致的 `Result` 函数中传播。整数解析要求消费完整文本，浮点还拒绝超出有限值
范围的结果；`true` 和 `false` 之外的文本不能偷偷变成布尔值。

随机数被刻意拆成两层。`std::random::Random::withSeed` 使用确定性状态机，同一种子得到同一序列，
测试和回放因此稳定；`fromEntropy` 所需的熵不写死在 VM 指令或内建表里，而由单独的
`glue/std_random.hpp` 经 `NativeRegistry` 注入。桌面可以接 `std::random_device`，
嵌入式宿主可以换成硬件随机源，无法提供熵的环境也能明确选择不绑定。

`std::path::PathString` 同样守住边界。`join`、`fileName`、`extension` 和 `normalize` 只处理文本，统一
分隔符并折叠 `.` / `..`，绝不顺手查询磁盘。文件是否存在、当前目录是什么、路径能否打开，
仍然属于宿主文件接口。

内存层只公开 `std::memory::MemoryStats`、`std::memory::Arena` 与 `std::memory::Span<T>`。Arena 在 VM 对象表里保存
自己持有的堆块地址，`reset` 或 `drop` 时成批释放；Magel 看得到的是 Span，不是 C++
`RuntimeObject` 的字段。释放后再通过旧 Span 访问会触发边界检查，而不是读到偶然留下的字节。

第一次全量样例还顺手揭开了两个旧问题。结构体“逐 8 字节槽拷贝”实际生成了 `store:i32`，
所以 `Result<float64, E>` 中的 `12.5` 会变成 `12.0`；改成显式 `store:i64` 后，浮点位模式和
宽整数才真正按位保真。随后，所有枚举构造器都叫 `__magel_enum_arg0`，而 StackVM 的类型表按
名字索引，不同泛型特化会彼此覆盖。构造器形参现在包含枚举名、变体名和载荷位置，类型不再
串线。静态工厂调用还与枚举构造器共用 AST 节点，生命周期判定也补上这一条，PathString 返回的
字符串终于能在块出口自动释放。

这轮最终通过 C++ StackVM **234 项断言**，以及 Magel **70 个正常样例 + 105 个错误
样例**。新增错误样例专门保留了 Arena 重置后访问旧 Span 的失败路径。四组 API 不算庞大，
但它们把一个更重要的原则写进了实现：标准库可以提供统一语义，宿主能力必须从明确的胶水
入口进入，VM 内部布局则留在边界以内。

## 第二十章 把边界写成一门小语言

标准库的宿主能力越来越多以后，手写一排排 `bindTyped` 开始变成新的重复劳动。问题不在
C++ 回调本身，而在同一份信息被写了三遍：Magel 里声明一次，C++ 里注册一次，文档里再解释
一次。任何一处名字、参数或泛型特化没同步，错误都要等到程序加载后才出现。

于是仓库里多了一种很小的胶水描述文件：`.mcpp`。它不替代 C++，只把 Magel 模块、宿主函数、
类型转换、接口实现、泛型绑定和变长参数写成可检查的数据，再由生成器产出 C++ 注册代码。
`std::math::Math`、随机熵源和标准容器一类宿主能力因此能在 `magel/glue/lang.mcpp` 里集中维护，
Magel 源码只看见标准库 API，不需要知道宿主函数地址。

导出工具也跟着改名为 `magel-emit`。名字变短不是重点，重点是职责变清楚了：它读取 Magel 编译
结果与胶水，当时规划过桌面 C++、嵌入式 C++ 和 Rust Cargo 工程；现在只导出前两种
C++ 目标。`magel-generator` 则把编译器、VM 模板和标准胶水装配成可再生成的工具链。
`clear` 命令只清理生成器自己认识的产物，不去猜用户目录里哪些文件“看起来多余”。

最后补上的不是新语法，而是一条资源边界。堆早已可以通过 `HeapAllocator` 换成静态 arena，
求值栈现在也能由宿主设置每个协程的槽位上限：

```sh
magel-emit program.quad --target embedded-cpp --heap-bytes 65536 --stack-slots 256
```

生成的运行器在启动 VM 前设置限制。超过上限会在执行现场报出槽位数、PC 与指令，不再把
宿主内存耗尽伪装成普通语言错误；不给参数时行为保持不变，仍使用动态、无显式上限的求值
栈。桌面和嵌入式因此共用同一套字节码语义，只由宿主决定资源预算。

后来 `.mcpp` 描述语言也被撤下：应用胶水回到普通 C++，动态库函数可以在 Magel 的
`abi` 块里集中声明。阶段快照很容易把过去的数字伪装成今天的事实；生成器的语言与模式
支持矩阵以 [`15`](15-language-mode-support.md) 为准，Magel 的语法兼容基线见
[EBNF 语法参考](https://github.com/rabbitc999/magel/blob/master/doc/33-ebnf.md)，用户 API 见 [`magel/README.md`](https://github.com/rabbitc999/magel/blob/master/README.md)；设计演进随语言
一起维护（`magel/doc/35-magel-story.md`）。故事可以记住为什么，源码和测试负责回答现在是什么。

## 第二十一章 给施工图加上名字

Magel 早已有 `%define`，但它只是一枚条件开关。糖糖刻意没有让它像 C 那样替换正文，因为同一
个名字既控制分支又改写表达式，出错时很难判断是哪一层动了手。正文宏后来使用另一套醒目的
`$macro NAME() … $end_macro`：先有定参块宏，再补对象宏、命名可变尾参和 `$delete_macro`。两套符号
因此各守一条边界，`%` 决定源码是否出现，`$` 决定出现的源码怎样展开。

真正麻烦的是 `#` 与 `##`。字符串化不能拿已经展开的结果，它要保存调用者写下的原文；词法
拼接也不能只删除宏体里的空格，因为逗号切出的实参本身可能带着前导空格。第一次测试
`prefix ## suffix` 时，展开结果仍是 `local Count`，解析器准确地在 `Count` 前停下。修复不是
给这个例子加特判，而是让拼接边界同时裁掉宏体空白与替换值边界，再把拼出的文本送回展开器。
于是 `SQU ## ARE(3)` 不仅能形成一个标识符，还能继续命中 `SQUARE` 宏。

很久以后，这两枚符号各多了一个把话说清楚的名字：`$concat(a, b)` 只拼标识符，两个实参都必须是
标识符，结果是标识符且不再参与展开；`$stringify(expr)` 只收一个表达式，捕获原文得到字符串字面量。
`##` 与 `#` 留在原位当兼容别名，新写的蓝图统一用 `$` 前缀——和 `$line` / `$file` / `$module` 排成
同一列元数据形式。检查也随之前移：实参不合格在宏展开阶段就报错，不必等展开完再猜。

字符串字面量也顺手回到文法层处理。`"x" "y"` 不由宏处理器偷改，而是由 IELR 文法里的
`string_literal` 在 AST 构造前合并；普通表达式和格式串走同一条规则。重新生成前端后没有
增加文法冲突，完整回归最终通过 **71 个正常样例 + 113 个错误样例**，其中错误路径覆盖非法
可变参数声明、固定参数不足、未知字符串化参数和缺少一侧的词法拼接。

这一轮留下的经验很朴素：宏可以改写源码，所以更应该有清楚的阶段、醒目的语法和失败即停
的诊断。能拼出名字不难，能让人知道名字为什么变成这样，才算把前处理器做完整了一点。

## 第二十二章 给切片软件留的位置

Magel 的语言特性快收口的时候，一个真实需求摆到面前：给一台打印机写切片软件。

先用一句话说清那台机器。连续碳纤维、柔性 TPU、普通耗材，三种料走同一套进给和同一个喷嘴。纤维要守着最大弯曲半径，TPU 要防回抽拉丝，普通料只要温度对了就不闹。三种参数互相打架，调好一种就顶坏另一种。这是台**融合怪**；没有现成经验可抄，谁都没把握一次做成。

需求方开出的条件听起来很轻巧：你写过解析器，切片不就那点事。

这话说对了一半，而说这话的人并不知道自己说对了哪一半。糖糖**确实**写过解析器 —— 只是那个仓库没人看过：没有外部评审，也没有甲方验收，东西只存在住处那台自攒的机器上。能把文本拆开的人，想来也能把模型拆开。

糖糖没说出口的是：切片软件是"一堆表 + 一堆几何"。层高排序、支撑面筛选、参数映射、耗材长度统计、悬垂点计数、填充路径起点随机化、候选路径挑选——这些恰好就是标准库缺的那几样。于是这一轮补的不是语法，是**工具**：

- `std::algorithms` 添了 `map` / `filter` / `reduce` / `sum` / `count`，和既有的 `fold` / `all` / `any` 同一套回调式内建；
- 取一个、洗一副收在 `std::algorithms::choice` / `shuffle`（`shuffle` 本来就是 `<algorithm>` 里的东西）——**洗牌不再需要递归写**；
- `std::math` 补齐 `floor` / `ceil` / `round` / `trunc` / `fmod` / `isNaN` / `isInf`，并且 `min` / `max` / `clamp` / `abs` 都有了 `int` 与 `float64` 两份重载：整数管栅格坐标，浮点管几何；
- `lang::Clock` 给单调时钟。切片是"算得越细越慢"，测速只能拿两次读数做差，不能看挂钟；
- `Random` 补了 `nextRange` / `nextBool`，配一个固定种子就能把"随机的填充起点"复现出来，出了问题能重跑同一份路径；
- 一元运算符 `+` / `-` / `~` 也能重载了。路径偏移里满屏的 `-v`，靠 `Negate` / `BitNot` / `Positive` 接口实现，和二元那套 `Add` 用的是同一条路；
- `?` 不再只认 `Result<T,E>`，`Option<T>` 这类**可空枚举**也能用：配置里查不到的参数、几何算不出的层，一路往上传，而不是拿 -1 当哨兵。

补这些的时候还顺手挖出一个一直挡路的类型错误：`-2.5` 被当成了 `int`。值本身没错（取负走的是浮点），错的是类型，于是 `auto x = -2.5` 推成整数、`abs(-0.5)` 算成 `0`、`{:3F}` 报"整数不接受浮点格式"。修法是一元运算的类型跟着操作数走。切片软件里 `-2.5` 这种写法到处都是，这个错早修比晚修好。

模块这边也改了一次。往编译器里新增标准模块（比如刚加的 `lang::Clock`）时，必须在编译器那张硬编码的"哪些 `lang::X` 是模块"的表里同步登记，漏了就报"自定义类型 X 用于 `lang::print` 时必须实现 `toString`"这种指错方向的错。现在这张表搬进文法里声明（`kMagelStdModules`），加模块改文法，不再改编译器实现。

Magel 当初借过 Rust 的不少想法：默认导出、接口当约束、`?` 传播错误、没有异常。现在它自己也在收口——固定宽度数值、泛型、接口、元组、模式匹配、错误传播、迭代器、协程、宿主模组，切片软件要用到的机关基本都在了。**Rust 那一边还在长**，Magel 这一边快写完了。

深夜的时候糖糖还在写这个仓库。白天的时间总是被切得很碎，一天里最好的精力未必轮得到这里，夜里的这几个小时才是自己的。他也清楚：一门语言能不能收口，不是他更努力一点就能决定的。

他能决定的只有一件事——语言这边该给的都给到位：算得动、测得准、查得到、传得出去、写得出来。剩下的交给几何和耐心。

## 第二十四章 名字可以少写，边界必须写清

那次更新，糖糖先改的不是窗口，而是一行最普通的赋值。

```c
int64 a = 1;
int64 mut& p = &a;
p = p + 1;
```

`a` 变成了 2，读 `p` 也得到 2。`p` 是可写引用，表达式直接读写它指向的元素。
曾经要在调用点辨认的星号退了场，结构体、枚举和接口的引用都用 `.` 访问成员。
只读引用写作 `T const&`；可写转只读可以隐式进行，反过来必须显式。

“那空引用放哪儿？”

答案落在类型上：普通引用必须初始化，不存在空引用；缺省值写成 `Option<T mut&>`。
`null` 退出关键字表，复合引用与地址算术也一并撤下，观察地址只走 `lang::address`。
这条规则还穿过了宿主边界：C ABI 的可空单对象指针由 `Option<引用>` 包装，
C++ 胶水用 `std::optional<Reference<T>>` 接住它，空值不能冒充有效引用。

下一块被改动的是循环。数组和列表的 `foreach` 变量直接读写源元素；自定义引用迭代器
返回 `Option<T mut&>`，有元素就交出引用，结束就交出 `None`。矩阵和数组都可迭代，
矩阵索引取列向量，向量索引取数值，矩阵、向量还可以与数组互转。
这些规则的例子和边界写进了[引用与迭代](https://github.com/rabbitc999/magel/blob/master/doc/04-references.md)。

然后轮到泛型的告示牌。

```c
T identity<T>(T value) { return value; }
struct Box<T> { T value; };

enum Choice<T> { None1, Value1(T value); };
```

类型参数统一跟在名字后面，函数、结构体、枚举、宿主类型和函数指针类型采用同一方向。
旧的 `generic<T>` 前缀不再接受，`generic` 本身成为普通标识符。
调用 `identity(7)` 时，编译器从实参推导类型；声明 `Choice<string> value = None1;`
时，左侧则告诉它这个空变体属于哪一种 `Choice`。同一个 `None1` 可以用于不同特化，
却不能在没有上下文时随便猜一个类型。载荷可以帮助推导，歧义与冲突必须报错。

糖糖没有把“省字”当成自动放行。函数指针的泛型也要特化，循环引用自身的函数指针类型
必须拒绝；枚举省掉前缀以后，声明、赋值、返回值、参数和 `match` 仍要指向同一种类型。
[集合与抽象](https://github.com/rabbitc999/magel/blob/master/doc/10-abstractions-and-collections.md)里留下了完整写法。

`match` 的分支也能用 `|` 连接多个备选模式，字符串范围补齐了四种开闭区间：
`['a','z']`、`['a','z')`、`('a','z']`、`('a','z')`。边界是否包含，直接写在端点上。

标准库也跟着换了零件。`std::binary` 读取二进制流中的基础数值、定长字符串和数组；
`lang::toInt32` 用 `Option<int32>` 表达失败，IEEE 754 转换支持 float32、float64、
大小端和数组重载。JSON、TOML 可以在 Magel 中解析。线性代数的 LU 等计算进入宿主胶水，
Magel 保留声明、类型选择与必要包装，裁剪统一使用 `NO_MAGEL_XXX`。

最后才轮到窗口。WinAPI 补齐了与 Qt 对应的 GUI 事件 ABI，Windows 默认加载 `mcgui.dll`，
`MAGEL_GUI_LIBRARY` 可以指定其他兼容后端。按钮、定时器与计算循环之间，仍是
“事件排队，VM 在指令边界交付”的约定。小车示例改用 `std::math`、`std::linalg` 和
`Ekf2.pose()`；GUI、小车、海龟的构建与测试统一由 Python 驱动，产物留在 `build/`。
机器人库的 AOT 导出还撞过 MinGW 目标文件节数限制，于是 Windows 编译补上了大目标文件支持。

截至 **2026-10-07**，这轮验收留下了可复查的结果：**144 个正常样例、192 个错误样例**
全部通过；覆盖 25 个标准库模块及机器人库的 **19 组样例**，在解释器、C++ VM、AOT 上
完成验证；GUI、小车和海龟通过 Windows 桌面端到端测试。线性代数的全部整数宽度由
解释器检查，导出使用 float32、float64 和 int64 代表类型。Qt 后端保留，本轮没有实测。

这次更新的故事到这里就有了落点：短下来的语法，要靠更明确的类型边界和跑过的程序支撑。
命令与覆盖范围放在[库迁移与回归验证](https://github.com/rabbitc999/magel/blob/master/doc/28-library-migration.md)，
语言变更记在 [Magel 变更记录](https://github.com/rabbitc999/magel/blob/master/CHANGELOG.md)。

## 第二十五章 公式也来敲门：CAS 与一个空格

这一次，糖糖在终端里写下的不是一段程序，而是一道题。

```sh
./build/cas/cas --eval 'd(x^3,x)'
```

屏幕回了 `3 x^2`。`x` 没有数值，计算却已经完成了一步。地图上于是又多了一扇门：
`cas/`，一个 C++17 符号计算系统。代数、微积分、矩阵、张量、数论和特殊函数进入数学内核，
ParseEngine 负责先把输入读成有结构的表达式。它后来也拆成了独立仓库，本仓库不再提供指向它的链接。


“表达式文法，计算器样例不是早就有了吗？”

真的公式比计算器样例多了几层机关：赋值、比较、隐式乘法、右结合的幂、阶乘、
函数参数、嵌套张量、范围、索引和切片。它们都写进 `cas.gram`，
内置符号逐个登记，产生式逐层组合，语义动作交给语义层构造节点。
逐语句读取与括号续行也通过 `%epilogue include` 固化进生成产物。
这份文法采用 SLR；生成报告里的冲突栏为空。

然后，一个空格把问题摆到了桌面上。

```text
f(x)
f (x)
```

旧规则把第一行读成调用，把第二行读成乘法。人只是给名称和括号留了一点距离，
解析器却换了一棵树。

糖糖定了规则：“字母后面带括号，就是函数调用。”

于是 `f(x)`、`f (x)` 都调用 `f`，`sin (pi/2)` 也照样得到 `1`。
要让符号乘括号里的表达式，就写 `x*(x+1)`；`2(x+1)`、`(x+1)(x-1)`
仍可使用隐式乘法。修改落在文法的函数名称词元上：名称后允许空白，再接左括号；
语义层去掉括号与末尾空白，剩下的名字用于查找符号。
函数定义、多参数调用和无参数调用跟着同一条规则走。

这条规则还找到了仓库里的旧公式。积分表中原先写作 `a (a+b*x)` 的乘法，
必须补上 `*`，否则新规则会把它读成调用。改解析器时，数据源也得跟着改。

积分表本身还有一道构建过程：259 条规则、777 个表达式由生成解析器读入，
编译成只读节点记录，运行时直接加载表达式树。公式留给人维护，节点留给程序使用，
求积分时无需重新读取磁盘上的规则文本。

树长出来以后，存储也要有归属。CAS 通过 `Cas::Memory` 接入仓库的
[自定义分配器库](../library/allocator/README.md)，数学节点、生成解析器容器和结果字符串
使用同一分配池；帮助模板也在构建期嵌入。命令行和 `Cas::Engine` 共用数学内核，
静态库可以交给其他程序调用。多个引擎仍共享进程级符号环境，调用需要串行进行。

最后一行不是“看起来对了”，而是 `make check`（在 CAS 独立仓库里跑）。
带空白与紧邻的调用、内置函数、自定义函数定义、显式与隐式乘法都有固定期望值，
全部 777 个积分表表达式还要逐项比对解析结构与编译后加载的结构。
这些检查通过了，才把那一个空格的故事收进文档。

生成器这次交出的，是一棵能继续求导、积分和变换的公式树。
文法里的边界写清楚，数学内核才能沿着正确的结构算下去。

## 第二十六章 流水线上的东西，总得有人接住

CAS 那棵树还放在桌上，Magel 的问题又排了过来。

“字符串、大数字、Set、Map、元组，都能引用。那引用字符串取字符，为什么还得写
`(*ref)[index]`？既然平常默认解引用，到了下标就不认了？”

糖糖把这条写到最前面：统一成 `ref[index]`。引用规则不能在每种容器门口换一块牌子。
字符串、大数与集合继续按值复制；`T mut&` 和 `T const&` 明确借用与可写性。
元组的成员仍只读，可写引用允许替换整个元组，不能因此偷偷开放普通成员赋值。

紧接着是两组大括号：Set 写 `{a,b,c}`，Map 写 `{key:value,...}`。
非空字面量能推导元素类型，空的 `{}` 要由上下文说明自己是哪种容器；元素按源码顺序
各求值一次。重复的 Set 元素只留下一个，重复的 Map 键保留最后一次写入的值。

“自定义键呢？总不能拿两个对象的地址判断是不是同一个键。”

键必须实现 `Equal<bool,T>`，回答值是否相等；`Hash<T>` 则可以实现，也可以不实现。
它提供 `uint64 hash(T value)`，用于快速筛选候选，哈希碰撞之后照样比较相等性。
没有哈希协议就走相等比较的查找路径。这两件事写进同一份规则，才不会今天说
‘哈希相同就是同一个’，明天又让没有哈希的键进不了门。

随后收掉的是名字旁边的脚手架。`string`、`String`、`lang::String` 统一指向同一个类型，
引用、元组和泛型参数里的拼写也跟着统一。`using` 语法被删除；核心 `lang` 自动可见，
导入库里不冲突的名字也能省略作用域限定符。程序自己声明的名字优先，多个导入来源
产生歧义时，再用完整限定名说明选哪一个。于是没有本地 `BigDecimal` 挡路时，
导入对应库后直接写 `BigDecimal` 就够了。

两种断言宏 `$assert_eq`、`$assert_neq` 曾加进来，后来又按要求删除。
今天写的是 `lang::assert`，没有冲突时也可以写 `assert`。旧语法的专门迁移提示也统一
清理：无效拼写按普通语法错误处理，已经释放的名字则按普通标识符规则判断。
这些收尾共同组成 **Magel 1.0 的语言基线**，不能再从旧章节里挑一条已撤下的规则使用。

最费工夫的，还是那条看起来最顺手的调用：

```magel
T3 result = t.f1().f2();
```

“内部就当它有一个中间变量。”糖糖说。

下面是降级思路，变量名只用于解释，不是要求用户照抄的源码：

```magel
T2 hidden = t.f1();
T3 result = hidden.f2();
```

`(t.f1() + 1).f2() + 2` 也一样，先接住括号里的结果，再继续调用。
以前让用户手写局部变量才能接住持资源的临时对象，现在由编译器安排求值和清理。
完整表达式结束后先保存最终结果，再逆序 `close` / `drop`、释放拥有资源并清空内部槽；
具名引用还需要借用临时来源时，相关所有者保留到声明块结束。
临时量可以藏起来，责任不能藏起来：移动只清走拥有资源的部分，枚举标签与普通数值字段
必须保留，否则下一步读取的就是一个被清坏的值。

这条地基稳了，`std::iter` 才能在上面铺流水线。`map`、`filter`、`take`、`zip`、
`fold`、`scan`、`try_fold` 等操作可以连起来；List 的 `iter()` 借用只读元素，
`iter_mut()` 借用可写元素，`into_iter()` 转移容器存储并让来源变空。
Set 和 Map 当前走值迭代，不把能改坏键规则的可写引用交出去。

“每过一道工序，都先装一整箱吗？”

“多数工序等到取元素才工作。`rev` 和 `peeking_take_while` 需要缓存有限来源，得另说。”

游标也有自己的值语义：复制迭代器得到独立的位置，引用迭代器仍借用同一份存储。
具名游标的 `next()` 等方法推进当前位置；`collect()`、`fold()` 的链式写法处理游标副本。
把这些区别写清楚，比把所有方法统称为‘消费迭代器’更有用。

具体接口与可运行样例见[标准迭代器](https://github.com/rabbitc999/magel/blob/master/doc/05-iterators.md)，
临时量的责任见[值语义与链式调用](https://github.com/rabbitc999/magel/blob/master/doc/03-value-semantics.md)，
集合的规则见[泛型与集合](https://github.com/rabbitc999/magel/blob/master/doc/10-abstractions-and-collections.md)。

## 第二十七章 四种数据库，验收不能只写一个“通过”

下一张清单不是语法，是库：“car、GUI、海龟都测一遍，还有其他外置库。”

测到 SQL 时，本机没有 MySQL。糖糖换了一个更容易在本地落地的入口：SQLite，
先用 `:memory:` 验证，再建文件、关闭、重开，检查数据真的留在磁盘上。
随后要求又加了两项：PostgreSQL，以及微软的 SQL Server。

于是 `std::sql` 保留原来的 MySQL 入口，又提供 SQLite、PostgreSQL、SQL Server
和通用 ODBC 入口。调用者面对同一套 `Database`、`ResultSet`、`DataCell`；
底下分别连接数据库原生客户端。**这是统一访问接口，不是自动翻译 SQL 方言。**

字符串引用也必须跟着连接走。MySQL 的反斜杠规则不能直接搬去 SQLite；
PostgreSQL 要按它的连接设置转义；SQL Server 的 Unicode 字面量要带 `N` 前缀。
因此多后端代码使用 `db.quote(text)`。旧的全局 `quote(text)` 保留 MySQL 行为，
它不会因为旁边多了一条 SQLite 连接就自动换规则。

第一个坑发生在还没执行 SQL 的时候：本机 SQLite 动态库需要显式初始化。
第二个坑是一条已经成功执行的 ODBC 建表语句，却返回 `SQL_NO_DATA`。
如果只认一种成功码，数据库已经把表建好，库却告诉用户失败。
再往后还要读长中文、emoji、64 位整数、NULL，区分文本 `"123"` 与数字 `123`。
ODBC 使用宽字符接口，长文本分段读取，不能拿一次缓冲区的大小当作字段的上限。

库回归也把编译器的老毛病带了出来。FFT 在解释器里通过，到了 AOT 却过不了误差检查。
查到最后，是 AST 的带类型字段读取把浮点类型丢成了整数；VM 运行时的数值处理掩盖了
问题，AOT 则照着错误的中间表示执行整数减法。

另一处发生在浮点比较：比较的两个输入是浮点数，输出却必须是布尔值。
AOT 的类型预扫描把输出也记成浮点，布尔函数指针的返回签名于是对不上。
修好之后，浮点字段运算和比较回调都进入固定回归，不能只看 FFT 这一次恢复正常。

“所以三个后端输出一样，才算到站。”

“还得说清楚它们连的是哪一个数据库。”

## 小结

这份外传讲的是一个人和几个 AI 搭档，把一张地图从「四种语言、十二种模式、97 个组合」补到
**六个完整后端 + Java / JS 两个 DD-Earley-CYK 窄后端、一个文法导出档、十六种模式、
384 份模板、155 个实测组合**。中间还删过东西、退回过一档，把 Rust 与 Go 完整加回，
又把 Java 按更诚实的边界接回来；随后补齐增量解析、Hydra86、严格 C-- 五次实验，以及
Magel 的类型化胶水、接口生命周期、泛型枚举、协程运行时、正文宏，以及 Parse / Random /
PathString / Memory-Arena / Text / Linalg 标准库。

Magel 后来又长了两段：一是 `std::event` 的**事件回调 / 中断 / 软件定时器**——事件异步发生、
在 VM 的指令边界交付，中断优先于线程与协程，`EventHandle` 把定时器和宿主事件统一成一种
事件源，GUI 与小车模拟器都接到这条线上；二是窗口层支持 **WinAPI / Qt** 两种后端，
`libmcguiqt.so` 只传定宽整数和 UTF-8 字符串，`gui::bindEvents(EventHandle)` 把 Qt 事件
登记成中断源，小车模拟器 `car_sim` 用同一份仿真逻辑配 WinAPI / Qt 两个后端（`USE_GUI_QT`）。
交付方式也收口了：`magel/stackvm` 与 `library/stackvm` 正式分叉、各自迭代，Magel 侧版本写进
`magel/VERSION`（当前版本 `1.2.0`，语言兼容基线 `1.0.0`），破坏性变更记 `magel/CHANGELOG.md`，
关键字、`match` / `Result` / `?` / `loop` 的拼写、接口名、生命周期与 `.svmb` v4 布局都算
冻结契约；通用验收入口为 `sh ci/run.sh`；逐库三后端和 Windows 桌面验证另有专项脚本。
2026-10-07 的 Magel 回归为 **144 个正常样例 + 192 个错误样例**，见第二十四章；2026-10-09 的 1.1.0 推进到 **155 个正常样例 + 268 个错误样例**，以及覆盖 27 个标准库模块的 22 个逐库样例，外置库与多数据库验收范围见第二十七章。1.1.1 补入完整表达式清理回归后，正常样例增至 **156 个**，错误样例仍为 **268 个**。各章的分阶段数字按当时读。

1.2.0 在文法中逐个登记十种复合赋值 Token 和产生式，通过 `M_CompoundAssign` 将 `A op= B` 展开为 `A = A op B`。纯 `a = b = c + 3` 链从右向左执行；包含复合赋值的链非法，包括 `a += b *= 3`、`a = b += 3` 及右侧加括号的形式。规则和正式样例见 [Magel 语言指南](https://github.com/rabbitc999/magel/blob/master/doc/01-language.md#复合赋值先计算再写回)。

Magel 后来把源码语法的兼容基线单独写进 [EBNF 语法参考](https://github.com/rabbitc999/magel/blob/master/doc/33-ebnf.md)。标准库拆成三层：核心 `lang.mgl` 自动加载、`std::xxx` 按需 `import`、`robot::` 等可选库；1.0 通过 `std::iter` 提供迭代链 API，程序可使用惰性适配器，也可显式使用 `foreach` 和 `lang::List<T>`。这也说明故事里某一阶段的功能清单，不能代替今天的语言规则。

CAS 则把同一台生成器接到了符号计算上：完整表达式文法、构建期编译的积分表、
自定义分配池和嵌入 API 一起落地。第二十五章记下了函数调用与隐式乘法的边界：
名称后接括号统一表示调用，符号乘括号要明确写出 `*`。完整用法与验证范围见 CAS 独立仓库的手册。
