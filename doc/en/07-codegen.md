# 04 Code Generation and Template System

> This is the English edition. The Chinese edition is the default and is the one maintained first — see [中文文档](../README.md)。

## 1. How the output artifacts are assembled

`Project::generateParserProject(ProjectRequest)` decides the artifact list, then calls
`CodeGenC99` / `CodeGenCpp17` / `CodeGenPython` / `CodeGenCsharp` / `CodeGenRust` /
`CodeGenGo` per target language to generate the full backend content; the Java and JS
backends dedicated to DD/Earley/CYK are generated by `CodeGenJava` /
`CodeGenJs` together with the shared `code_gen_narrow.cpp`, and finally everything is handed to
`Project::writeParserProject`, which creates directories and writes files.
`ProjectRequest` carries in the grammar, the lexer, analysis results, precedence, `%code ... %endcode` user code,
the semantic value type declared by `%value_type`, `%union`, the `%copy` list, and so on, all at once
(see `source/include/ParseEngine/project.hpp`).

The artifact list is hard-coded in `source/src/project.cpp`:

```cpp
const std::vector<std::string> k_projectFiles = {
    "parser.h",      "parser.c",       "parser_token.h", "parser_token.c",
    "parser_user.h", "parser_table.c", "main.c",         "Makefile",
    "CMakeLists.txt", "RESULT.md"};
```

When none of `%code ... %endcode` / `%value_type` / `%union` is present, `parser_user.h` is removed
from the list (`parser.h` provides a default `typedef int ParserValue_T;`). Files copied in via
`%copy` are appended to the end of the list.

**`%mermaid` / `--mermaid` adds a set of `mermaid/` state-machine diagrams to the list**
(`Mermaid::projectFiles`, see [`06-analysis.md`](../06-analysis.md) §5.4). It is unrelated to teach
mode (`%teach`): `%teach` only changes the report content, while `%mermaid` only governs this set
of files; both switches are off by default, and the command line can override each one's grammar-side
setting:

| File | Content |
| --- | --- |
| `mermaid/index.html` | Overview page: all diagrams embedded in one page, with legend and cross-links |
| `mermaid/grammar.html` | Grammar LR automaton (LR item sets + GOTO + state coloring) |
| `mermaid/lexer.html` | DFA for each `%token regex` / `%identifier` (not generated when there are no regex Tokens) |
| `mermaid/grammar.mmd` / `mermaid/lexer.mmd` | Mermaid source of the same two diagrams |

They are **newly added files** and are independent of the target language (the content is the same
across all tiers, and the extensions are kept as-is); artifacts such as
`parser.c` / `parser.cpp` / `Parser.cs` are unaffected. When `%mermaid` is not enabled, or when neither diagram can be drawn (LL(1) with no regex Token),
this set of files does not appear in the list at all; `--dump-mermaid` goes to standard output and does not pass through the artifact list.

## 2. Template inlining

Every piece of C code, the `Makefile`, and the `RESULT.md` skeleton in the artifacts lives in `source/templates/`
(**384 files in total, all `.tmpl`**):

- **`.tmpl`** — the format of the `library/template` template engine (`{{ variable }}` / `{% if %}` /
  `{% for %}` / `{% include %}` / `{# comment #}` / `{% raw %}`); the generator calls
  `tmpl::renderValues()` to render (see §3). **Purely static fragments with no variables use it
  too** (for example `csharp_csproj.xml.tmpl`: the target framework number `net8.0` is written directly
  in the template, and the generator is only responsible for pulling it out without changing a single
  character; **the exception is when the file header carries a `{# … #}` description block** — that
  kind must go through the engine once, otherwise the comment leaks into the artifact as-is). **Everything goes through `.tmpl`**: C99's `c99_*` (50),
  C++17's `cpp17_*` (68), Python's `python_*` (51), C#'s `csharp_*` (49),
  Rust's `rust_*` (53), Go's `go_*` (55), Java's `java_*` (2), JS's
  `js_*` (3), the shared fragments `code_gen_*` (3),
  8 build scripts (`Makefile_*` 4 + `CMakeLists_*` 4), `RESULT.md` (1),
  21 `result_*.md` fragments, and 20 `mermaid_*` templates.
  - **`.template`** — placeholder format (the template writes `__placeholder__`, and the generator fills it with `replaceAll`). The generator
    still supports it; all templates shipped with the repository are already `.tmpl`.

> The C99 batch uses file names of the form `c99_<original name>`, among which `c99_lexer.c` / `c99_parser_token.c` /
> `c99_parser_table.c` share the same name as the **artifact file name** — when renaming a template, do not rename the artifact along with it.

The two share the same key by "the name with the suffix stripped" (`Utils::loadTemplate("RESULT.md")` matches
both suffixes; when the names collide, `.tmpl` takes precedence and prints a reminder). At build time,
`tools/embed_templates.py` generates them into `source/src/templates_data.cpp`:

- Sort by file name and use the suffix-stripped name as the key (on a name collision `.tmpl` overrides `.template`);
- Store the content as a raw string literal `R"PGX(...)PGX"`, and assert that the content does not contain `)PGX"`;
- Generate `ParseEngine::embeddedTemplates()`, returning an `unordered_map<string,string>`.

At runtime, `Utils::loadTemplate(name)` looks up the inline table first, then lets
`SCRIPT_ENGINE_TEMPLATES=<directory>` override it (during development you can read templates from disk directly without re-inlining).
`source/src/templates_data.cpp` is a generated file; do not edit it by hand. After changing templates, run:

```sh
python3 tools/embed_templates.py     # 等价于 make -C source templates
```

## 3. Placeholders and sections

The two template kinds are filled in different ways:

- **`.template` (placeholder format)**:
  - **Whole replacement**: placeholders of the form `__XXX__` are replaced once by the local `replaceAll` with generated content.
  - **Section extraction**: the template wraps a section with `__SEC_NAME_BEGIN__` / `__SEC_NAME_END__`,
    and `CodeGen::extractSection(template, "NAME")` extracts that section (for example
    `DEFINES`, `ERROR_TYPE`, `TOKEN_TYPES` in `parser_prologue.c`).
      Only the C backend still uses this scheme.
- **`.tmpl` (template engine format)**: the template itself writes `{{ name }}` to fetch values, `{% if %}` branches,
  `{% for %}` loops, and `{% include "name" %}` to splice in fragments; the generator only arranges the data as "name → value"
  (`source/src/project.cpp` includes `template/engine.hpp` and goes through `tmpl::renderValues` /
  `tmpl::encode`; the fragment table for `{% include %}` is the third argument of `tmpl::renderValues`).
  When the artifact needs to contain the target language's own `{{` / `}}` (for example `%code ... %endcode` inside a comment), wrap it in
  `{% raw %}…{% endraw %}`, otherwise it will be consumed as a variable tag; when a block tag occupies a whole line, the whole line is deleted,
  so there is no need to write an inline variant of `{% if %}` just to save a blank line in the template.

**The shared part (`source/src/code_gen.cpp`) also has three fragment templates** — the pieces of
C/C++ code that every backend tier needs are no longer written into C++ as string literals:

| Template | What it renders | Engine features used |
| --- | --- | --- |
| `code_gen_action_cases.cpp.tmpl` | One `case Nu: { … break; }` semantic-action branch per production (`CodeGen::actionCases`) | `{% for %}` iterates over productions, `{% if %}` selects the `#line` variant and the default statement for empty actions |
| `code_gen_line_back.txt.tmpl` | The "restore line" `#line <next line> "<artifact name>"` (`resolveLineDirectives`) | `{{ }}` |
| `code_gen_section_marker.txt.tmpl` | The section markers `__SEC_<name>_<BEGIN/END>__` (`sectionMarker`) | `{{ }}` |

The `cases` of `code_gen_action_cases.cpp.tmpl` is an **array of objects**: the
`ActionCase` in `source/src/code_gen.cpp` binds the five fields `id` / `has_line` / `line` / `empty` /
`action` via `TEMPLATE_MODEL(...)`, and the template writes `{{ c.id }}`, `{% if c.has_line %}`. This is the
first place in `source/src/` to use a "model class + `{% for %}`" (the other artifact templates all pass ready-made strings or
arrays produced by `tmpl::encode`).

Two lessons (you will trip over these when writing this kind of fragment template):

- **Who owns the newline**: when `{% endfor %}` is written on the same line as the previous line's content, that line's newline is *after* the tag
  and belongs to outside the loop body, so one separating newline is missing between iterations; you must let `{% endfor %}` occupy its own line
  (the whole line deleted) to get the effect of "each iteration ending with a newline".
- **Trailing newline of fragment templates**: template files conventionally end with a newline, but a fragment is **spliced into another artifact as a value**,
  so one extra newline means one extra line; therefore after rendering you must strip the trailing newline — in `code_gen.cpp`
  everything goes through `renderValueTemplate()` (render + strip the trailing newline).

  The replacement order matters: when placeholder names are prefixes of one another (for example `__CUSTOM_LR_LOOP_TREE_ACCEPT__` and
  `__CUSTOM_LR_LOOP_ACCEPT__`), replace the longer one first or rename them so they do not collide on the prefix, otherwise they will be truncated and replaced wrongly.

## 4. The single semantic value runtime

There is only one semantic value runtime, and it is also the default (writing `%runtime` produces an error). Its key points:

| Item | Description |
| --- | --- |
| Additional artifact | With `%code ... %endcode` / `%value_type` / `%union`, there is one extra `parser_user.h` |
| Semantic value type | The user-provided `ParserValue_T` (POD): declared by `%value_type`, or `%union` with per-symbol members, or typedef'd by you in `%code ... %endcode` |
| Parse entry point | `int32_t Parser_RunText(const char *, ParserValue_T *)` |
| Action translation | Generated as ordinary C expressions/operators; no type checking at generation time |
| Memory | The user is responsible for semantic values; the tree nodes of `%tree` go through `malloc/realloc/free` |
| `%tree` | A node is a `ParserTree_T`, storing only the name and lexeme, decoupled from the semantic value type |

Actions accept only ordinary C expressions and operators; no type checking is done at generation time. Constructs outside
the supported range produce a generation-time error pointing to "please implement it yourself in C inside `%code ... %endcode`".
For the full list of generation-time checks, see
[`05-grammar.md`](../05-grammar.md) §5.


**Error recovery** is the second layer of runtime logic, decoupled from the analysis layer (see
[`06-analysis.md` §2.11](../06-analysis.md#211-error-列与-sync错误恢复在分析层的落点)):

- `Parser_LRRecover` in `c99_custom_lr_runtime.c.tmpl` implements a two-layer strategy — the `error`
  production (`#ifdef PARSER_TOKEN_ERROR`, pushing a zero-initialized placeholder value without consuming lookahead) takes priority,
  and the `%sync` panic mode (`#ifdef PARSER_HAS_SYNC_TOKENS`, calling `Parser_LRPanicReduce` before popping to reduce the
  pending items on the stack, then discarding input up to a sync Token) serves as fallback;
- `c99_custom_ll_loop.c.tmpl` implements top-down panic mode: ① the stack top can accept the current Token →
  alignment complete; ② the current Token is a `%sync` anchor → pop until it can be accepted; ③ the stack-top item
  "should end here" (the current Token is in its FOLLOW) or an item deeper down can accept it → abandon the construct to which the stack-top item
  belongs (popping down to the inner frame as well, `Parser_LLDiscardFramesFrom`); ④ if nobody accepts it, discard the
  Token. ②③④ share a budget of 256 steps. FOLLOW is provided by the generator-emitted `s_ParserFollow`
  (a 0/1 table of non-terminal × terminal; in C++17 it is `kLlFollow`, in Python `_LL_FOLLOW`);
  LL(0) has no information about "who the current Token belongs to" and falls back to stopping at the first error.
- On the generator side, `syncPredicateC` generates, per `%sync`, the `PARSER_HAS_SYNC_TOKENS` /
  `Parser_IsSyncToken` (LR mode adds one more, `Parser_LRCanShiftSyncToken`)
  fragment (placeholder `__CUSTOM_SYNC_PREDICATE__`, accepted by both the LR / LL runtimes);
  `%sync` itself does not enter the analysis layer;
- The multi-error table is in `c99_parser_c_custom.c.tmpl` (`s_ParserErrors` + `Parser_SetError` /
  `Parser_GetErrorCount` / `Parser_GetError`), and the capacity macros
  `PARSER_MAX_ERRORS` / `PARSER_ERROR_RECOVERY_TOKENS` are in
  `c99_parser_prologue.c.tmpl`; semantic values discarded on pop consult the `%destructor` dispatch table
  (`Parser_DiscardValue`, written in `generatorDestructorDispatchC`) first, and only when the symbol has no
  `%destructor` bound do they fall back to the optional `PARSER_USER_DISCARD_VALUE` hook;
- The `__SEC_DEFINES__` section of `c99_parser_prologue.c.tmpl` also provides memory hooks:
  zeroing / copying in the generated code always writes `PARSER_MEMSET` / `PARSER_MEMCPY`,
  which default via `#ifndef` to `<string.h>`'s `memset` / `memcpy`; users can substitute their own implementation in
  `%code ... %endcode` or via a compile-time `-D` (the C++17 artifacts do not generate these two macros).

**Where `%epilogue` is inserted** (in the finishing loop of `generateCustomProject`):

- The assembly order is "template renders `parser.c` → `collapseBlankLines` + `__MODE_NAME__` replacement →
  finally append the `%epilogue` body". The insertion point is **after** the closing brace, so user-defined functions stay in the
  global scope and other compilation units can link to them as usual (matching the declarations in `parser_user.h`);
  C++17 goes through `generateCpp17Project`: after `CodeGenCpp17::parserCpp()` produces `parser.cpp`,
  `appendEpilogue()` appends the body, inserting a line `using namespace <namespace>;` before the body and pasting the
  body **verbatim** (without rewriting), so a `%epilogue` using C99 names (`Parser_RunText` /
  `ParserError_T`) can still call the generator-produced functions — C++17 artifacts come with a compatibility layer;
- Therefore there is no need to insert internal boundary markers into `parser.c`: appending at the end is equivalent to "two-part" mode, and the
  markers do not leak into the artifact and are unaffected by `collapseBlankLines`;
- `%main` takes a different path: `CodeGenC99::customMainCWithBody()` uses the `main_custom.c` template
  (the `stdio` / `string` / `parser.h` shell is unchanged) to replace `__DEMO_MAIN__` with the user body;
  with 0 sections it still goes through `customMainC()`.

The division of labor among the four "places to write user code" (the most common consequence of putting code in the wrong place is a link-time duplicate definition or multiple
`main`s):

| What to put there | Where it goes | Why |
| --- | --- | --- |
| Declarations, `typedef`, macros, `static inline` functions | `%code ... %endcode` → `parser_user.h` | It is included by both `parser.c` / `parser_token.c`, so only things that are "harmless to include repeatedly" may go here |
| Ordinary function definitions, `static` helper functions | `%epilogue` → end of `parser.c` (or `parser.cpp` in C++17) | Appears only once; under C++17 it stays outside the namespace (so other compilation units can link to it), the body is prefixed with `using namespace` and pasted verbatim, and the compatibility layer lets it call generator functions directly |
| `main` | `%main` → `main.c` | Choose one of this and the built-in demo main, to avoid two `main`s |
| Standalone compilation units (`.c` / `.h`) | `%copy` | Copied into the artifact directory and added to the Makefile / CMakeLists; include your own headers yourself |

Counterexample: putting a non-`inline` function definition into `%code ... %endcode` → `parser_user.h` is included by multiple `.c` files →
multiple definition. Positive example: `example/epilogue_demo.gram`.

### 4.1 custom + `%union`: semantic values with per-symbol C types

When `%union` is written, `ParserValue_T` is provided by the generator,
and is **appended after the user's `%code ... %endcode` code**:
  do not start function / type names with `Parser_`, otherwise the calls in actions will fail to find a declaration on the `parser.cpp` side;
  just switch to another prefix (the one used in `example/union_demo.gram` is `Demo_MakeNode`).
- When `%union` is not written, this code is not touched at all: the artifacts are the same as before adding `%union`.

#### Interaction between terminals and the lexer

With `%union`, `ParserToken_T.value` is also switched to `ParserValue_T` (see the full shape table in
[`08-generated-code.md`](../08-generated-code.md) §10), so the lexer can write lexemes directly into members according to `%token <member>`: numeric
Tokens write the parsed value, double-quoted strings, identifiers (including `%identifier`) and `%token regex` write the matched text, and fixed
literals write nothing.
When `PARSER_USER_TOKEN_VALUE` is not defined, `Parser_UserTokenValue()` is changed to directly
`return pToken->value;`; if the user defines the macro, that still takes precedence.

Implementation notes at generation time:

- The member name is fetched by `lexMemberOf()` from the "symbol → member" table; the three built-in
  terminals `NUMBER` / `STRING` / `VARIABLE` are looked up by name, and `%token regex` generates a
  `switch (bestType)` in the same index order as `s_ParserRegexTypes`.
- Numeric Tokens no longer wrap `(int32_t)`: `pToken->value.<member> = (value);`, letting C's implicit
  conversion land `long` / `double` on the member's own type.
- When `%union` is written but `NUMBER` is not bound to a member, there is no place for a number in the union, and the template's four
  statements `pToken->value = (int32_t)(…)` (assigning an `int` to a union will not compile) are deleted entirely:
  `PARSER_MEMSET` has already zeroed the Token, so the semantic value of numeric Tokens is thus always zero, and C++17
  artifacts leave a comment at the same spot explaining this. Generation time also emits a `warning:` (only when the grammar really uses
  `NUMBER` and `NUMBER` still goes through the built-in numeric lexing). When `%union` is not written, `value` is
  `int32_t` and these four statements are kept as before.
- Regex and identifier Tokens only have text on hand, so what is written is the address of `pCtx->lexeme` — it is the lexer's
  reused buffer and will be overwritten by the next Token; copy it yourself if you need to keep it.
- `parser_token.h` needs to see `ParserValue_T` before `ParserToken_T`: it includes the user header with
  `#ifndef PARSER_USER_HEADER_INCLUDED / #define … 1 / #include "parser_user.h" /
  #endif`, and `parser.h` adds the same `#define` under `%union`; whichever of the two entry points expands first wins.
- When there is no `%union`, none of this is generated: `value` is still `int32_t`, and `parser_token.h` does not change by a single
  byte.


```c
/* parser_user.h —— 用户代码在前：%union 可以引用这里定义的类型 */
struct Node { int value; struct Node *next; };
#define PARSER_USER_TOKEN_VALUE(pToken) ((ParserValue_T){ (int)((pToken)->value) })

/* —— 生成器追加的语义值类型：body 原样来自文法 */
typedef union {
    int          ival;
    struct Node *node;
} ParserValue_T;
```

Order is crucial: `%union` members can reference types `typedef`'d / `struct`'d by the user in `%code ... %endcode`, so user
code must come first. With only `%union` and no `%code ... %endcode`, `parser_user.h` is still generated,
and the default `typedef int ParserValue_T;` is no longer injected; when neither is present, behavior is as before.

`$n` / `$` are automatically expanded to the per-symbol bound member (`ActionTranslator` + `UnionValueSpec` pass the
"symbol → member" and slot correspondences into the translator):

| Form | No `%union` (as before) | With `%union` |
| --- | --- | --- |
| `$` (LL(1)) | `result.value` | `result.value.<member of the LHS symbol>` |
| `$` (SLR / LALR / LR(1) / IELR) | `result.value` | `result.value.<member of the LHS symbol>` |
| `$n` (LL(1)) | `values[n]` | `values[n].<member of the nth symbol>` |
| `$n` (SLR / LALR / LR(1) / IELR) | `stack->values[stack->top - k + n - 1]` | same as above plus `.<member of the nth symbol>` |
| `+ - * / %`, comparison, bitwise | generate the C operator directly | unchanged (after member access it is a scalar, and the operator applies as usual) |

`%destructor <member> { ... }` goes through another translation entry: the fragment is likewise collected verbatim, but only `$$`
is recognized (`translateDestructorBody` replaces token by token and leaves `$$` inside string literals untouched), expanding to
"the value currently being discarded" — the C artifact renders it as `pValue->member`, and so does the C++17 artifact. Writing
forms that need right-hand-side symbols such as `$1` / `$line` is a generation-time error. The dispatch table itself is generated by
`generatorDestructorDispatchC` (C) / `generatorDestructorDispatchCpp17` (C++17), both sharing the "member →
symbols bound to it (symbol name + unified symbol number)" grouping computed by `CodeGen::destructorSymbolGroups`. For the artifact shape see
[`08-generated-code.md`](../08-generated-code.md) §10.1.

A few corner cases:

- No C type checking at generation time: a type mismatch in `$$ = $1` is not caught, and is left to the C compiler to warn / error.
- Hand-written member access like `$n.<member name>` / `$n.<field name>` passes through as-is (only
  `$n.<scalar type name>` is intercepted with a hint), so users can use either automatic expansion or write it themselves.
- `$n = expression` (assigning to a right-hand-side symbol) is an error, and the message carries the production number and the character
  position within the action — a RHS symbol's semantic value belongs to itself, and `yacc` does not allow this either.
- The batch of built-in forms of the builtin runtime has been removed, and writing them produces an error (for the list see
  [`05-grammar.md`](../05-grammar.md) §5); when `%union` is written, the error message adds one more hint
  (please write `$n.<member name>` directly).
- LL(1) left-recursion elimination moves the left-recursive step into `LEFT_LOOP`: in a `left_continue` production
  `$1` is the accumulated value (the symbol is the LHS non-terminal rather than the rewritten RHS first symbol), and only from `$2` on
  do they correspond to the rewritten RHS symbols. Member lookup follows this slot correspondence, see the handling of
  `production.transform == "left_continue"` in `generatorActionCases`.
- Productions with empty actions (as the LR virtual start production is) generate under `%union`
  `memset(&result.value, 0, sizeof(result.value));` — a union cannot use `= 0`.
- Actions in C++17 artifacts generate `result.value` / `stack->values[...]` (empty actions switch from
  `memset` to value initialization `result.value = ParserValue_T{};`), corresponding one by one to the C artifacts;
  this difference is controlled by one switch in `CodeGen::actionCases(..., cpp17)`, and C and C++17
  share the same translator; Python goes through the dialect switch of `ActionTranslator` (see §10.2).
- The generator does not rewrite a single character of user code (`%code ... %endcode` / `%epilogue`), so functions /
  types defined there should **not** start with `Parser_` (that prefix is reserved by the generator and the C++17 compatibility layer). Just
  switch to another prefix (for example `Demo_MakeNode`).

### 4.2 The `#line` directive: pointing compiler errors back to `.gram`

The generator inserts a pair of `#line` directives before and after all "code coming from `.gram`":

```c
        case 3u:
        {
#line 10 "example/calc.gram"
            result.value = stack->values[stack->top - 1u + 0u];
#line 511 "parser.c"
            break;
        }
```

The first line marks "the next line" as line 10 of `.gram`, and the second gives the line number back to `parser.c` itself.
Insertion points:

| Content | Placement | Forward `#line` points to |
| --- | --- | --- |
| Semantic action | In the action branch of `parser.c` | The line where the action `{` is |
| `%code ... %endcode` | `parser_user.h` | The first line of the body |
| `%union` body | Inside the `typedef union { … }` of `parser_user.h` | The `%union` line |
| `%epilogue` body | End of `parser.c` (or `parser.cpp` in C++17); under C++17 outside the namespace, with one extra `using namespace` line before the body | The line after `%epilogue` |
| `%main` body | `main.c` (or `main.cpp` in C++17) body | The line after `%main` |

Line number source and implementation notes:

1. **The line number is the original file line number**: `GrammarLoader` converts using `SourceLines` during parsing (byte offset →
   preprocessed line → original file line), so a whole line dropped by `%if` does not make the line number drift; a multi-line action only marks its
   starting line, and the following lines are left for the C compiler to increment on its own.
2. **Placeholder + backfill**: the assembly phase only writes `@@SE_GRAMMAR_FILE@@` (the `.gram` path) and
   `@@SE_LINE_BACK@@` (the restore line), and the finishing loop finally calls
   `CodeGen::resolveLineDirectives(text, grammar path, artifact name)`:
   - The forward line is replaced with the path the user passed to `--grammar-file` (with `\` and `"` escaped), keeping the relative /
     absolute form unchanged;
   - The restore line is replaced with "the line where this directive is + 1" and the **final artifact name** (`parser.cpp` / `main.cpp`;
     `parser_user.h` has the same name in both languages).
3. **Backfill happens in the last step**: `generateCpp17Project` only calls `resolveLineDirectives` one by one after
   `parser.hpp` / `parser.cpp` / `main.cpp` / `parser_user.h` are all assembled (including `%epilogue`), so the line numbers and artifact names
   are final; the `.gram` path is never touched by the renaming logic.
4. **Not added to purely generated content**: `Makefile` / `CMakeLists.txt` / `RESULT.md` contain not a single `#line`
   (you can verify directly with an example without semantic actions such as `pl0.gram`); the same applies to the C-produced
   `parser_table.c` / `parser_token.c` / `parser.h`.

Every one of the above can be verified with real error line numbers from `gcc` / `g++`. Example:
`example/line_demo.gram`.

**Python artifacts: a comment instead of `#line`.** Python has no `#line` directive (errors only give the artifact's own line
number), so the same positions become a comment line `# 语法文件 <grammar file> 行 <N>`, pointing to exactly the same line numbers as
C's `#line`:

```python
        if production == 3:
            # 语法文件 example/calc.gram 行 10
            result.value = values[0] + values[2]
            return STATUS_OK
```

Four placements: semantic actions (inside the `_apply_action` branch, with indentation following the action body at 12 spaces),
`%code` (top of the `parser.py` module), `%epilogue` (end of `parser.py`),
`%main` (start of the `main.py` demo body). On the generation side there are only two functions:
`CodeGenPython::grammarLineMarker(line)` assembles that comment line (the path likewise written first as the
`@@SE_GRAMMAR_FILE@@` placeholder), and during finishing, `generatePythonProject` /
`generateLexPythonProject` directly replace the placeholder with the real path — **not going through
`resolveLineDirectives`**, because that one escapes C string literals, which is not needed in a comment
(Windows backslashes are kept as-is), and letting it rewrite the restore line as `#line` is also unacceptable (Python would produce a syntax error).

### 4.3 Lexer generation for whitespace Tokens and `%space`

The lexers of the three backends all look like this: skip whitespace before fetching a Token, then match in the order "string →
regex + fixed literal longest match → number → identifier". The key point is that **the whitespace-skipping step must also recognize
literals** — otherwise a declared `%token NL "\n"` would never match (the whitespace has already been skipped). The generation scheme:

- The fixed-literal rule table (C's `s_ParserLexRules` / C++17's `kLexRules` / Python's
  `_LEX_RULES`) carries two extra flags per entry: `blankFirst` (the first byte is whitespace or a `\b` wildcard) and
  `wildcard` (contains a `\b` wildcard). The former is used by the whitespace-skipping loop, and the latter decides whether the lexeme should be copied from the
  input on a hit (the literal stores the placeholder byte `0x1F`, not the real character).
- The whitespace-skipping loop is **generated**, not a fixed template: when `%space` is not written and there is no
  literal starting with whitespace / `\b`, the classic `isspace` loop is output as-is (the lexing behavior of such grammars stays consistent,
  except that the literal rule table has two more flag fields);
  otherwise it is swapped for a loop of "decide by the `%space` set + stop when hitting a literal that starts with whitespace", and the
  set (a `strchr` constant string in C / C++17, `_LEX_SKIP_CHARS` in Python) and the
  hit-test function (`Parser_LexRuleHit` / `lexRuleHit` / `_lex_rule_hit`) are generated together.
- When decoding a literal, `\b` is written as the placeholder byte `k_blankWildcardChar` (`0x1F`), and the hit-test function
  treats it as "any one whitespace character"; the `varCString` of C / C++17 writes control bytes as
  three-digit octal (`\037`), to avoid C's `\x` escape greedily eating the following character.
- The three values of `%space`: not written (defaults to all whitespace), written (use the declared set, with `\b` expanded to six
  whitespace characters), or written as `""` (the empty set, skipping nothing). Generation time has already expanded `\b`, so at runtime
  only ordinary character tables are consulted.

`%space` appears only in the lexers of C / C++17 / Python; semantic values, parse tables, and action translation are unaffected;
in `%tree`, the lexeme of a whitespace Token is the real whitespace character from the input (for example
`NL(\n)`, `SP(\t)`).

## 5. `%tree`

- A node is `ParserTree_T { pName, pText, ppChildren, childCount, childCapacity }`,
  storing **only the symbol name and Token lexeme**, not the semantic value, managed with `malloc/realloc/free`;
  the templates are `custom_tree_api.h`, `custom_tree_helpers.c`, `custom_tree_ll1.c`,
  `custom_lr_tree_body.c`, `custom_lr_tree_api.c`, `lr_tree_header.c`.
- The tree is fully decoupled from the semantic value type: no change to `%value_type` / `%union` affects the tree interface.

## 6. `%copy`

`GrammarLoader` parses `%copy [file|dir] path` into a `CopySpec`, with relative paths resolved against the directory containing the grammar
file:

- `file` (default): copy to the artifact directory, keeping the basename;
- `dir`: recursive copy, keeping the directory hierarchy;
- Copied-in `.c` / `.h` files (plus `.cpp` / `.hpp` for C++17 artifacts) are appended to the generated
  `Makefile`'s `LIB_SRCS` / `HDRS` respectively.
- Copied-in source files are also appended to the `add_library(parser ...)`
  source list of the generated `CMakeLists.txt` (expanded in the template by `{% for src in copy_sources %}`).

When writing artifacts, `writeParserProject` automatically creates parent directories for paths with subdirectories.

### 8.1 The shape of C++17 artifacts (Qt style + standard library)

- **One namespace holding one set of classes**: inside `namespace Parser` are `class Engine` (Qt-style
  d-pointer, `std::unique_ptr<Private> d`), `class Tree`, `class Error`,
  `struct Token`, `enum TokenType`, `enum class Status`;
- **Standard library data structures**: `std::string_view` (views over the input and lexemes), `std::string`,
  `std::vector`, `std::unordered_map`, `std::unique_ptr`;
- **`inline constexpr` in place of `#define`**: `kValueSlots` / `kMaxStackDepth` /
  `kMaxErrors` / `kErrorRecoveryTokens` are all constants in the namespace;
- **Parse tables and lexer tables** are represented as `std::int32_t` / `std::uint16_t` arrays (`kAction` /
  `kGoto` / `kLexRules` / `kRegexDfas` …), from the same generation-time data as the C target;
- **Custom allocators are not supported**: there are no `PARSER_USER_*` release hooks, semantic values are copied by value, and the syntax tree's
  ownership is `std::unique_ptr`, with the destructor doing the release;
- **Compatibility layer** (`source/templates/cpp17_compat.hpp.tmpl`): the namespace additionally provides
  `PARSER_OK` / `PARSER_ERR_*` / `PARSER_MAX_*`, `ParserError_T`,
  `Parser_RunText` / `Parser_Run` / `Parser_GetLastError` / `Parser_GetError`,
  all sharing one process-level `Engine` underneath (**not thread-safe**). This way code written in `%main` / `%epilogue`
  in the style of C artifacts compiles without changes.

### 8.2 How lexing and the action sequence are generated

- The lexer blocks (`source/templates/cpp17_lexer*.tmpl`) correspond one to one with the C target's blocks, but use
  `std::string_view` slicing, `std::isdigit(static_cast<unsigned char>(...))` and other
  C++ idioms; fixed literals go through `kLexRules`, and `%token regex` / `%identifier` / `%commit`
  go through the standard library `<regex>` (`kRegexRes` / `kIdentifierRe` / `kCommitRes` +
  `lexRegexMatch()`, see §13);
- The LR driver (`cpp17_lr_stack.cpp` / `cpp17_lr_loop.cpp`) uses `struct LrStack` to store
  **state + semantic value + variable name + tree node**, and `$n` translates to `stack->values[stack->top - k + n - 1]`;
- The LL(1) driver (`cpp17_ll.cpp`) replicates the C target's semantic frames with `LlFrame` / `LlStack`;
- Diagnostic text matches the C target word for word (the mode short name comes from the template variable `{{ lr_name }}`, Token type names, expected sets).

### 8.3 Namespace and file name prefix: `%namespace` / `--namespace`

`CodeGenCpp17::namespaceName` / `filePrefix` decide the namespace name and file name prefix
(`GrammarConfig::cppNamespace`, with the command-line `--namespace` taking precedence; empty = `Parser` + no prefix):

- The header guard macro is generated from the artifact file name (`parser.hpp` → `PARSER_HPP`, `myapp_parser.hpp`
  → `MYAPP_PARSER_HPP`) — a prerequisite for multiple instances coexisting;
- In `parser.hpp`, both the `#include` of `parser_user.h` and the `#line` restore lines use the prefixed name;
- Artifact names in `Makefile` / `CMakeLists.txt` / `RESULT.md` are replaced by `renameProductFiles()`
  (`libparser.a` / `parser_demo` / `%copy` files are untouched, and the scripts themselves are not prefixed);
- When the prefix is empty, the artifact names are `parser.hpp` / `parser.cpp` / `main.cpp` / `parser_user.h`;
- `%namespace` is C++17-only: pairing it with `--lang c` errors out directly (it does not silently ignore it).

Example `example/namespace_demo.gram`.

### 8.4 `%cpp_only`: declaring that this grammar can only target C++17

When a grammar depends on things only present in C++17 artifacts (`Engine` / `std::string_view` / the compatibility layer), write:

```text

```

The command line `--lang c` (or `%lang c`) is intercepted with an error, to prevent anyone from mistakenly assuming the C artifacts also

## 9. Python language backend (`--lang python`)

The most direct use of Python artifacts is **quick analysis of a grammar**: with no compiler to install, `python3 main.py` shows the
parse result, error messages, and syntax tree of the same grammar on the same input. Like C / C++17, it is "another set of templates + another backend".

It is also the tier best suited **as an interface for AI / scripts**: a coding agent (a terminal-equipped assistant such as Codex / Claude Code) can get the
parse result with `printf '...' | python3 main.py` or `python3 -c "import parser; ..."`, and the output is usually only a few lines — no need to paste
long logs or the whole input into the context, nor to read the grammar and artifacts into the context. The "edit grammar → regenerate → look at result" loop

### 9.2 The Python dialect of semantic actions

When `ActionTranslator` is constructed it takes one extra `python` switch (the corresponding argument of
`translateAction(...)`); when on, the same Pratt parser produces Python expressions instead of C expressions:

| Action form | C / C++17 generates | Python generates |
| --- | --- | --- |
| `$$` | `result.value` (or `$$.<field>`) | `result.value` (the out-parameter `result` of `_apply_action`) |
| `$1` `$2` … (LR) | `stack->values[stack->top - n + 1]` | `values[n-1]` (a sliced copy of the RHS) |
| `$1` `$2` … (LL) | frame slot | `values[n]` |
| `&&` / `\|\|` / `!` | as-is | `and` / `or` / `not` (writing `and` / `or` / `not` directly is also accepted; the precedence of `or` / `and` is ordered per Python semantics) |
| Statement terminator | `;` | no semicolon |
| `yyerrok` / `yyclearin` | `Parser_LrYyErrOk()` / `Parser_LrYyClearIn()` | `self._yy_err_ok()` / `self._yy_clearin()` |

Because semantic values are just ordinary Python objects, `values` passes a **sliced copy of the right-hand-side semantic values**:
actions that only read `$n` + write `$$` (the style used by all the example grammars) are fully sufficient; writing back to values directly on the stack
(beyond `$$ = $1 + 1`, also writing back `$1`) is not a usage supported by Python artifacts.

The Token semantic value convention given by the lexer: string Tokens are a `str` with quotes removed and escapes decoded,
numeric Tokens are `int` / `float`, identifiers and fixed literals are the lexeme text, and the EOF and `error`
pseudo-Tokens are `None`.

### 9.3 User code and indentation normalization

Python has no preprocessing layer and no `parser_user.h` landing spot, so the body goes directly into `parser.py`:

```
import sys

# ---------- %code ... %endcode（用户正文） ----------

<归一化后的用户代码>

# ============ 状态码 ... ============
```

`CodeGenPython::normalizeUserCode()` is the sole entry point for this section; `%code ... %endcode` /
`%code … %endcode` (`parserPy`, done block by block with a blank line between blocks), `%epilogue` and `%main`
(`generatePythonProject` / `mainPy`) all go through it. It does three things:

1. Eat trailing `\r` and strip leading/trailing blank lines;
2. Remove the common indentation by the **minimum** leading whitespace width of all non-blank lines (tab counted as 4 columns) — grammars are often
   written with layout-driven indentation, and pasting that directly at module top level is an `IndentationError`;
3. Replace the remaining leading tabs with 4 spaces (to avoid mixing tab / space within the same piece of code).

No character other than leading whitespace is touched, so multi-line strings and comment content are preserved as-is. When there is no user
code, this section is not inserted.

### 9.4 Forms rejected at generation time and `%class`

`CodeGenPython::checkPythonSupported` (`source/src/code_gen_python.cpp`) uniformly intercepts these C-only forms before
generation, with errors carrying the original file line number and no silent ignoring: `%value_type` (`valueType`),
`%union` (`unionBody`; `%token <member>` / `%type <member>` both require `%union`, so they are intercepted along with it), `%namespace` (`cppNamespace`). On the command-line side, `source/src/main.cpp` intercepts once earlier as well,
to make the error messages more direct.

`%class NAME` / `--class NAME` decides the parser class name; parsing and validation are in
`source/src/grammar_loader.cpp` (`GrammarConfig::pythonClass`, together with `pythonClassExplicit`
to distinguish "an empty string was written" from "nothing was written"): first check the Python keyword table (`pythonKeywords()`), then
validate against `[A-Za-z_][A-Za-z0-9_]*`. Pairing it with `--lang c` / `--lang cpp17` errors out directly
(to change the name of C++ artifacts use `%namespace`). The artifact file names are independent of the class name and are always
`parser.py` / `main.py` (`CodeGenPython::parserFileName` / `mainFileName`).

### 9.5 Consistency with C / C++17

The three artifacts share the same generation-time data (ACTION / GOTO / lexer tables / action translation), so the same
grammar (when it does not use the C-only forms above) produces word-for-word identical output on the same input: error codes, line/column
numbers, error message text, and `%tree`'s tree text all line up. The user bodies all **have no
`#line`** (Python errors rely on its own traceback), and the demo program prints one extra line
`解析结果: <repr>` when `result` is not `None` (the C demo only prints it if the user defines
`PARSER_USER_DEMO_PRINT_VALUE` in `%code ... %endcode`). Example: `example/python_demo.gram`.

### 9.6 LR(k) / LALR(k): second-level ACTION table and k-Token window

With `%mode lrk` / `%mode lalrk` and k > 1, all three backends generate by the same scheme (at k = 1 the generated
code is as before, and neither the second-level table nor the window appears):

| Backend | Table (generated by `code_gen*.cpp`) | Runtime (template) |
| --- | --- | --- |
| C99 | `s_ParserAction` (shift) + `s_ParserReduce` (reduce/accept) + `s_ParserLookaheadCode` / `s_ParserLookaheadColumn` (column index) | `source/templates/c99_custom_lr_runtime.c.tmpl`, `c99_custom_lr_item_types.c.tmpl` |
| C++17 | `kAction` + `kReduce` + `kLookaheadCode` / `kLookaheadColumn` | `source/templates/cpp17_lr_loop.cpp.tmpl`, `cpp17_core.cpp.tmpl` |
| Python | `_ACTION` + `_REDUCE` + `_LOOKAHEAD_CODE` / `_LOOKAHEAD_COLUMN` | `source/templates/python_lr.py.tmpl`, `python_engine.py.tmpl` |

Key points:

- **The columns are not "number of Tokens ^ k"**: columns are created only for the k-tuples actually used by the grammar, encoded into integers and arranged in order,
  with a runtime binary search; so even k = 3 does not blow up the table.
- **The window head is always "the current Token"**: `current` (in C++17 `m_current`, in Python
  `_current`) plus the following k-1 Tokens. `yyclearin`, "discard lookahead" in error recovery, and
  advancing the main loop all just move the window, shared by `%tree` / Token array mode / text stream mode.
- **Lexing may run ahead**: in text stream mode the window fetches k-1 extra Tokens in advance, so a lexical error
  may be reported earlier than at k = 1 (an inevitable consequence of k > 1).
- **Error recovery only consults the shift layer**: shifting the `error` pseudo-Token and the `%sync` sync Token both consult the first
  layer directly (the `Parser_LRCanShiftSyncToken` criterion is also it); panic reduce, however, scans **all**
  reduce columns when k > 1 — when an error occurs the window is often not in any lookahead set (which is exactly how
  LR(k) finds errors early), so consulting only the current window's column would find no reducible item at all.
- After changing these templates you **must** re-run `python3 tools/embed_templates.py`.

### 9.7 LL(k) / LL(0): the predictive parse table creates columns per k-tuple

Artifacts of the LL family have only one predictive parse table, and all variation in k falls on the **column
axis** (the LL table generators in `code_gen*.cpp` + the `custom_ll_*` / `cpp17_ll.cpp` / `python_ll.py` templates):

| k | Columns | Runtime column index |
| --- | --- | --- |
| 0 (LL(0)) | only one column | always 0 (does not look at lookahead) |
| 1 (LL(1)) | one column per Token (dense table, byte-for-byte the same as before) | `current.type` |
| ≥ 2 | one column per k-tuple actually used by the grammar | binary-search the column by the encoded k-tuple of the window |

Difference from the LR side: LR has two tables ("shift layer + reduce layer"), while LL has only one, but the meaning of a column
is likewise a k-tuple. What both ends share:

- **Window**: `Parser_FillLookaheadWindow` / `Parser_AdvanceLookahead` (C),
  `fillLookaheadWindow` / `advanceWindow` (C++17), `_fill_lookahead_window` /
  `_advance_window` (Python) — LL and LR each have their own, with identical semantics: the window head is always
  `current`, and advancing shifts the whole thing left and appends one new Token.
- **Column encoding**: $\sum_i \mathrm{TokenNo}_i\cdot(\text{number of Tokens})^i$ (the low-order term is the window head),
  sorted at generation time and binary-searched at runtime.

For LL(0) / LL(1) the column index is computed directly (0 / the Token number), but those two column-encoding tables still generate one
placeholder element, purely so that the table-lookup function in the template compiles (C uses `#if` tiers, C++17 / Python
use runtime constants). In addition, error synchronization of the LL family uses the same column index: a production in that column of the table means
"the stack-top non-terminal can accept this window" (FIRST, or the FOLLOW of a nullable non-terminal — those columns of
ε productions). The FOLLOW of non-nullable non-terminals is not in the predictive table; the generator separately emits a
`s_ParserFollow` / `kLlFollow` / `_LL_FOLLOW` for FOLLOW set recovery (see the "error recovery" subsection above in §10).

## 13. Generation details of `%commit` and the position info API (six tiers)

`%commit` / `%trivia` and `ParserLocation` / `current_location` land on two layers:
at **generation time** the rules are compiled into tables and the "lexical declaration order" is written into the tables; at **runtime** the
same longest-match logic decides "whether this text is a Token, gets collected into a container, or is discarded", and maintains the position of the current
lookahead. The **algorithm** is identical across the six tiers, but **who matches the regex** differs:

| Backend | Regex matcher | Tables in the artifact |
| --- | --- | --- |
| C99 | Generated DFA or the shared ordered runtime | the character-class partition of `s_ParserRegexDfas` / `kLexClassMap` |
| C++17 | `std` / conservative `dfa` / shared `vm`; shared Unicode | `kRegexRes` / `kIdentifierRe` / `kCommitRes` + `lexRegexMatch()` |
| Python | the standard library `re` | `_REGEX_RULES` / `_IDENTIFIER_RE` / `_COMMIT_RES` + `_lex_regex_match()` |
| C# | `System.Text.RegularExpressions.Regex` | `_REGEX_RE_LIST` / `_IDENTIFIER_RE` / `_COMMIT_RE_LIST` + `_lexRegexMatch()` |
| Rust | Rust's official `regex` crate (`regex = "1"` in `Cargo.toml`) | `_REGEX_RES` / `_IDENTIFIER_RE` / `_COMMIT_RES` + `lex_regex_match()` (each compiled once inside a `OnceLock`) |
| Go | the standard library `regexp` (RE2) | `sParserRegexRes` / `sParserIdentifierRe` / `sParserCommitRes` + `sParserLexRegexMatch()` (`regexp.MustCompile` compiles each once at package-level variable initialization) |

Across targets, distinguish matching order from character domains:

- The C/C++ shared runtime supports `\b` word boundaries. Byte mode uses ASCII word characters; `(?u)` uses fixed Unicode 17.0 semantics. Native libraries may use different character domains and Unicode versions.
- Ordinary C DFA rules take the longest accepting prefix. Ordered runtimes and most native libraries follow branch and greedy/lazy order inside one rule; the lexer then compares lengths and declaration order across rules. Patterns such as `a|ab` are not automatically equivalent across engines.
- C++ `dfa` optimizes only a proven ASCII subset, otherwise all byte rules fall back to the standard library. `vm` uses shared execution throughout, and explicit Unicode rules always use the shared path.

See [regex compatibility](../21-regex-compatibility.md) for each rule's engine, unverified native semantics and rejection reasons.
`--check` validates generation in memory; `--strict-regex` rejects native rules without proven shared equivalence.
C and C++ `vm` require successful shared compilation. Unrecognized native extensions may warn and proceed, but known unsupported capabilities are rejected.
The shared bounded-repeat limit is 1000; nullable patterns are rejected.

### 13.1 Lexical matching (the same order across six tiers)

1. Skip `%space` whitespace before fetching a Token;
2. Do a longest match among "fixed literals + `%token regex` + `%commit` / `%trivia`":
   literals are tried first in descending length order, and regex and commit each take "the longest match starting from the current position"
   (C uses DFA or shared ordered execution; C++ selects its configured engine; other targets use native regexes,
   and all require "must start from the current position" — C++17 uses `match_continuous`,
   Python's `pattern.match` is anchored by nature, C# additionally checks `Match.Index == start`,
   Rust uses `Regex::find_at` and then confirms `m.start() == start`, Go uses
   `FindStringIndex` and then confirms `loc[0] == 0`);
3. **On equal length, compare by "lexical declaration order"**: `%define` / `%token` / `%token regex` /
   `%commit` / `%trivia` share one auto-incrementing number (written into the tables at generation time: for C it is
   `ParserLexRule_T::order` / `s_ParserRegexOrders` / `s_ParserCommitOrders`,
   for C++17 `LexRule::order` / `kRegexOrders` / `kCommitOrders`, for Python
   `_LEX_RULES_ORDER` / the 4th item of `_COMMIT_RES`, for C# `_LEX_RULES_ORDER` /
   `_COMMIT_ORDERS`, for Rust `_LEX_RULES_ORDER` / `_REGEX_ORDERS` /
   `_COMMIT_ORDERS`, for Go `sParserLexRulesOrder` / `sParserRegexOrders` /
   `sParserCommitOrders`);
4. When a commit hits, it consumes the raw text: `skip` (`%trivia` / `%commit skip`) discards it, and the rest
   is collected into the container as `append{line, type, text}`, then it **continues to fetch the next Token**;
5. Each of the six tiers keeps one minimal matching entry point: C99's `Parser_LexDfaMatch`, C++17's
   `lexRegexMatch`, Python's `_lex_regex_match`, C#'s `_lexRegexMatch`,
   Rust's `lex_regex_match`, Go's `sParserLexRegexMatch`.

### 13.2 How the container and position API are expressed in the six tiers

| | C99 | C++17 | Python | C# | Rust | Go |
| --- | --- | --- | --- | --- | --- | --- |
| Container element | `ParserCommit { int line; const char *type; char *text; }` | `ParserCommit` (`std::string` fields) | `ParserCommit` namedtuple | `parser.Commit` (`final` fields) | `ParserCommit` (`line` / `kind` / `text`) | `ParserCommit` (`Line` / `Type` / `Text`) |
| Container | `ParserCommitList` (`items` / `count` / `capacity`) | `std::vector<ParserCommit>` | `list[ParserCommit]` | `List<Commit>` | `Vec<ParserCommit>` | `[]ParserCommit` |
| Get container | `Parser_GetCommits()` | `Engine::commits()` | `engine.commits` | `engine.Commits` | `engine.commits()` | `engine.Commits()` |
| Release | `Parser_FreeCommits()` (`text` is `malloc`; `type` is static, do not free) | standard library (none) | reference counting (none) | GC (none) | ownership (none) | GC (none) |
| Position type | `ParserLocation` | `ParserLocation` | `ParserLocation` namedtuple | `Parser.Location` (`readonly struct`) | `ParserLocation` (three fields) | `ParserLocation` (three fields) |
| Get position | `Parser_CurrentLocation()` | `Engine::currentLocation()` | `engine.current_location()` | `engine.CurrentLocation` | `engine.current_location()` | `engine.CurrentLocation()` |
| Token offset | `ParserToken_T::offset` | `Token::offset` | `token.offset` | `Token.offset` | `token.offset` | `Token.Offset` |
| Tree node position | `Parser_TreeGetLocation(node)` | `Tree::location()` | `Tree.location` | `Tree.Location` | `Tree::location()` | `Tree.Location()` |

Details:

- **offset is always a UTF-8 byte offset**: C99 / C++17 walk the byte buffer directly;
  Python accumulates `len(ch.encode("utf-8"))` per character, and Go accumulates `len(string(ch))`;
  C#'s strings are UTF-16, so it accumulates as "ASCII 1 / two bytes 2 / three bytes 3 / surrogate pair 4".
  All six tiers align with C99's byte offset.
- **Tree node position**: a leaf node is the Token's start; a branch node takes its first child that has a position,
  and all six tiers compute it on demand (building the parent first and filling the children later also works); when none has one it is 0 (C#'s
  `tree.location()` returns `null`) meaning unknown.
- `$line` / `$column` in all six tiers now read the position API (C is `Parser_CurrentLocation()`,
  C++17 is `currentLocation()`, Python is `current_location()`,
  C# is `CurrentLocation`, Rust is `current_location()`, Go is `CurrentLine()` /
  `CurrentColumn()` — the latter few read the position API internally) — the values are the same as before.
- Lexer-mode artifacts (`%mode lex`): C99 exposes
  `Parser_LexGetCommits(&lexer)` / `Parser_LexFreeCommits(&lexer)`; the lexer instances of C++17 / Python /
  C# / Rust / Go also carry the same set of `commits` / `location` interfaces
  (Rust / Go are `Commits()` / `CurrentLocation()`; in a lexer's `Parser` there is only
  the error table + lexer + `tokenize`).

### 13.3 Artifact tables of %commit (generation time)

| Target language | Lexer rule table field | commit table |
| --- | --- | --- |
| C99 | `ParserLexRule_T::order` | `s_ParserCommitDfas` / `s_ParserCommitTypes` / `s_ParserCommitSkips` / `s_ParserCommitOrders` (`PARSER_COMMIT_COUNT`) |
| C++17 | `LexRule::order` | `kCommitRes` / `kCommitTypes` / `kCommitSkips` / `kCommitOrders` (`kCommitCount`) |
| Python | the 5th item of `_LEX_RULES` | `_COMMIT_RES` (`(regex, type name, whether skip, declaration order)`) |
| C# | `_LEX_RULES_ORDER` | `_COMMIT_RE_LIST` / `_COMMIT_TYPES` / `_COMMIT_SKIPS` / `_COMMIT_ORDERS` |
| Rust | `_LEX_RULES_ORDER` | `_COMMIT_RES` (`OnceLock<Vec<Regex>>`) / `_COMMIT_TYPES` / `_COMMIT_SKIPS` / `_COMMIT_ORDERS` |
| Go | `sParserLexRulesOrder` | `sParserCommitRes` (`[]*regexp.Regexp`) / `sParserCommitTypes` / `sParserCommitSkips` / `sParserCommitOrders` |

When `%commit` / `%trivia` is not declared, artifact behavior is as before (C# and Python do not even use `count`,
relying directly on an empty table / empty array; C++17 / C99 use a 1-element placeholder table + `count = 0`).
**The Go tier is more frugal**: it turns "is there `%commit`" into a template switch — when there is none, that matching code block
is not generated at all, and the tables are not emitted either (things like `sParserCommitRes` only appear when there really is `%commit`).

| Artifacts | ① the input `.gram` (**exported byte for byte**, the file name follows the input file; when no file is given it is the built-in `default_grammar.gram`, exported as `grammar.gram`) ② its analysis report `<grammar name>.analysis.md` (`pl0.gram` → `pl0.analysis.md`) ③ `RESULT.md` (generation info + artifact list + how to use), plus `%copy` files |
| Assembly | `generateGramProject()` in `source/src/project.cpp` + `generatorGramAnalysisMd()` / `generatorGramResultMd()` (`Project::generateParserProject` takes this path before the mode branch) |
| Modes | All 16 modes can be exported; the report varies with the mode (LL predictive table / LR state machine and ACTION-GOTO / GLR multi-path / Earley-CYK chart / `lex` Token table), see [Support Matrix](../15-language-mode-support.md) for details |
| Report | `<grammar name>.analysis.md` = generation info (source grammar / exported files / mode) + conflict resolution + unresolved conflicts + the full text of the analysis report from `--report` (`request.reportText`, identical word for word to `--report`); `RESULT.md` only says what was produced and how to use it, and does not repeat the report |
| Inapplicable directives | `%namespace` / `%class` / `%package` / `%import` / `%class_body` / `%destructor` / `%cpp_only` in this tier all **emit one hint and are ignored** (no code is generated, so there is no landing spot; `%cpp_only` only constrains code generation) |

The problem it solves: when the artifact directory contains only the generated source, "which grammar did this code come from,
and what was the analysis result at the time" can only be answered by going back to the command line. The export tier nails the two together, convenient
for archiving / committing / handing over to other tools; the analysis report becomes its own file, paired with the `.gram` (`pl0.gram` ↔
`pl0.analysis.md`), and its content is exactly the one from `--report`, so there is no need to store it separately.

```sh
# 只要文法 + 分析报告（默认 ielr）
ParseEngine example/pl0.gram --out-dir /tmp/pl0_gram --lang gram
ls /tmp/pl0_gram      # pl0.gram  pl0.analysis.md  RESULT.md

# 换模式再导一次：报告就是那一套分析（这里看 LALR 的冲突）
ParseEngine example/ielr_demo.gram --out-dir /tmp/ielr_gram --lang gram \
    --mode lalr --teach
```
