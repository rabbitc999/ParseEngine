# 正则兼容性与生成前校验

每次生成的 `RESULT.md` 都包含逐规则的正则执行报告，列出 `%token regex`、
`%identifier`、`%commit`、`%trivia` 的实际引擎、字符模式、使用能力、选择原因及
预算支持。固定字面量和内建数字、字符串不属于这个报告的分析范围。

```sh
ParseEngine example/regex_budget.gram --check --lang cpp17
ParseEngine example/regex_budget.gram --check --cpp-lexer vm --strict-regex
```

`--check` 在内存中完成文法分析和产物生成校验，打印正则报告，不创建输出目录，
也不写入、清理或更新已有产物与清单。显式指定的 `--report FILE` 仍会保存分析报告。
它不调用目标编译器，也不执行原生正则库，因此不能代替生成产物的构建和运行测试。
遇到已知不支持的正则，返回非零退出码，并在报告中标明规则与原因。

## 引擎如何选择

| 目标与配置 | 实际选择 |
| --- | --- |
| C | 纯 DFA 规则使用生成表；任意规则需要有序语义或包含非 ASCII 原文时，整个显式正则集合切换到共享有序运行时 |
| C++ `std` | 字节规则使用 `std::regex`；显式 `(?u)` 规则使用共享 Unicode 运行时 |
| C++ `dfa` | 全部规则都属于已证明等价的保守 ASCII 子集时使用 DFA；任意规则不满足时，全部字节规则回退到标准库；Unicode 规则仍使用共享运行时 |
| C++ `vm` | 全部显式规则使用共享有序运行时，分别保留字节和 Unicode 模式 |
| Python、C#、Rust、Go、Java、JavaScript | 使用各自原生正则库；字符域和 Unicode 版本取决于目标库 |
| `gram` 导出 | 保留正则文本，不执行正则 |

C++ DFA 报告和实际生成共用同一套资格判断。报告也区分“某条规则有默认预算”与
“全部显式规则可配置共享预算”：混合标准库和 Unicode 规则的 C++ 词法器属于前者，
不能声称所有规则都受到共享预算保护。具体接口见 [20 正则资源预算](20-regex-runtime-budgets.md)。

## 严格模式的范围

`--strict-regex`（别名 `--strict`）拒绝尚未证明与共享规范等价的原生规则。
共享实现以及原生库中已确认的保守 ASCII 子集可以通过；复杂原生规则即使目标库能够
执行，也可能被严格模式拒绝。“原生，未完全确认”表示语义保证范围，不表示表达式必然有错。

默认生成允许这类原生规则，同时在报告中保留说明。已知不能执行的组合在普通模式也会
报错，例如 Rust/Go 的前瞻和反向引用、C++ 标准库的后顾、当前 JavaScript 后端未转换的
全局模式前缀，以及 Python 内建 `re` 不支持的共享 Unicode 属性转义。
该检查是保守的已知能力分类，不是每种原生语法的完整验证器。

严格模式仅约束显式正则，不证明内建词法规则、语义动作、目标类型或整份解析器跨语言等价。
使用原生扩展时，可以保留普通模式并构建目标工程验证；需要固定共享语义和资源预算时，
选择 C 或 C++ `vm`。

## 回归入口

```sh
python tests/regex_compatibility.py
sh ci/run.sh
```

测试覆盖整体引擎切换、九种目标报告（八种代码目标加文法导出）、严格模式、已知不支持
能力、混合 Unicode 的预算说明、表格特殊字符转义，以及校验前后输出文件逐字节不变。
