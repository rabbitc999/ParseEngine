# lztext

把程序内嵌的大段文本（代码模板、内嵌标准库、运行时资产）**压缩后存进二进制**，
运行时再解压，用来缩小可执行文件体积。纯 C++17，不依赖任何第三方库
（不用 zlib / liblzma / OpenSSL）。

## 为什么是这个算法

在本仓库的真实语料上实测（整体拼接打包，比率 = 压缩后 / 原始，越小越好）：

| 算法 | ParseEngine 模板 1.09 MB | magel 内嵌资产 1.48 MB | 自实现的代价 |
|---|---|---|---|
| brotli -11 | 0.150 | 0.161 | 静态字典约 120 KB，直接吃掉收益；解码器上千行 |
| bzip2 -9 | 0.151 | 0.160 | BWT 解压要 5~6 倍块的内存 |
| lzma -9 | 0.152 | 0.162 | 范围编码 + 上下文建模，复杂度高一个量级 |
| zstd -22 | 0.154 | 0.166 | FSE/tANS 解码器上千行 |
| deflate -9 | 0.232 | 0.221 | LZ77 + 哈夫曼，但**窗口上限只有 32 KB** |
| **lztext** | **0.172** | **0.185** | 解码器约 150 行、编译后约 5 KB |

关键在于另一次实测——**字典（窗口）大小对压缩率的影响**：

| 字典大小 | ParseEngine 模板 | magel 资产 |
|---|---|---|
| 32 KB | 0.210 | 0.200 |
| 64 KB | 0.193 | 0.188 |
| 256 KB | 0.163 | 0.174 |
| 1 MB | 0.151 | 0.163（之后饱和） |

对代码类文本，**把窗口开大比换更强的熵编码更划算**。所以本库：

- LZ77 的匹配窗口取**整个输入**，不受 32 KB 限制——这是它明显优于 deflate 的原因；
- 熵编码只用**规范哈夫曼**，不引入算术/范围编码，解码器因此很小。

结论：压缩率接近 lzma，代码复杂度接近 deflate，净收益最好。

## 用法

```cpp
#include "lztext.hpp"

std::string text = "...";
std::vector<unsigned char> packed = lztext::compress(text);   // 构建期
std::string back;
bool ok = lztext::decompress(packed.data(), packed.size(), back);  // 运行期
```

`compress` 会自动比较：压缩后不比原文小，就按"原样存储"（method 0）输出，
所以小文本、随机数据也不会越压越大。

构建期内嵌脚本不要自己实现压缩算法，直接调用 `lztext_pack`，
保证"压缩/解压只有一份 C++ 实现"：

```sh
lztext_pack  <输入文件> <输出文件>     # 压缩（写完立刻解压回读比对）
lztext_pack -d <输入文件> <输出文件>   # 解压
```

## 容器格式

```
magic  4B    "MLZ1"
method 1B    0 = 原样存储，1 = LZ77 + 哈夫曼
usize  varint（LEB128）解压后的字节数
[method == 1]
  主字母表码长：273 个符号 × 4 bit   （256 字面量 + 1 结束符 + 16 长度桶）
  距离字母表码长：25 个符号 × 4 bit  （距离桶 0..24，最远 2^25 - 1）
载荷    按位打包（高位在前）的符号流，以结束符收尾
```

长度桶 `b` 覆盖 `[2^b + 2, 2^(b+1) + 1]`，距离桶 `b` 覆盖 `[2^b, 2^(b+1) - 1]`，
两者都按 `floor(log2(x))` 定位，不需要查表。

## 构建与自检

```sh
make          # 构建并跑自检：往返一致性 + 边界用例 + 12 组随机语料模糊测试
make pack     # 只构建命令行打包工具
make clean
```
