# 通用文本预处理器 · 技术报告（Rust 版）

> 本报告写的是 **`library/preprocess-rust` 这个独立 Rust crate（`preprocess`）**：
> 它的模块划分、关键实现取舍、与 C++ 版的类型映射、自检方式，以及**范围边界**
> （哪些明确不做、哪几处有意不同）。用法与快速开始见 [README.md](README.md)。
>
> 面向的读者：想知道「[`library/preprocess`](../preprocess/README.md)（C++17）搬到 Rust
> 里长什么样」的人——包括想照着改、想对照两份实现、想拿它当别的 DSL 的预处理层的人。
>
> **一句话结论**：两边同一套行为。CLI 在同一批输入、同一批参数下跑 **56 组对照**，
> `-o` 产物逐字节、stdout、stderr、退出码全部一致；自检断言条数两边都是 **102**。

## 1. 目标与范围

**目标**：把 `library/preprocess`（C++17 的 `preprocess.hpp` / `preprocess.cpp`，
`preprocess` 命名空间）翻译成 Rust，**只用标准库**，并且做到「翻译不走样」——
指令语义一样、默认选项一样、诊断短码一样、输出逐字节一样、自检用例一样。

**做到什么程度**：

- 指令全集：`symbol` / `unsymbol`、`define` / `undef` / `undefine`（按前缀与开关决定
  是否算符号定义）、`if` / `ifdef` / `ifndef` / `elif` / `else` / `endif`、`include` /
  `include_once` / `import` / `once` / `pragma once` / `error` / `warning`；
- 语言无关的扫描：指令前缀集合、行注释串列表、块注释串对、字符串定界符、
  成对的「不解析区域」（`OpaqueRegion`）；
- 条件表达式：`|| && ! ()`、`NAME == / != 字面量`、`defined(NAME)`，真假判定与
  `--define` 一致；
- 包含：当前文件目录 → `include_dirs` → 原样，三条都找不到才报 `include-not-found`；
  默认「只展开一次」、循环检测、最大深度；
- 可插拔包含加载器（CSV / 数据库 / 内存文本）：`Default` / `UseFile` / `Inline` /
  `Skip` / `Error` 五种返回；
- 行号：默认空行占位（行号一一对应）+ `line_map` 来源表 + 可选 `#line` 标记；
- 诊断：19 个稳定短码，出错不中断、一路收集；
- 命令行：C++ 版 `main.cpp` 的全部选项，退出码 0 / 1 / 2，诊断走 stderr；
- 自检：16 个 `#[test]` / **102 处断言**（与 C++ 版逐条对应）+ 7 个单元测试 +
  1 个真跑的文档示例；`cargo clippy --all-targets` 无提示。

**明确不做**（不是待办）：

| 不做 | 说明 |
| --- | --- |
| 宏展开 / 参数化宏 | 符号只有「有没有 / 值是什么」两件事，不做 `#define F(x)` 那种文本替换。C++ 版就没有，Rust 版保持一致——本库是**行级的条件与包含处理器**，不是 C 预处理器 |
| 表达式里的算术 / 下标 / 字符串函数 | 表达式只有逻辑、比较与 `defined`。想算别的东西，用条件表达式挡在 `include` 前面 |
| 校验被引用的外部文件 | `include "表.csv"` 里的 CSV、`%copy` 的路径这类**引用**，库一律不打开（LSP 那边的结论同理）：它只有文本，没有文件系统语义 |
| 多字节字符的「字符」级语义 | 下标、行内列号、表达式列号全是**字节**偏移（与 C++ 版一致）。见 §4.1 |
| 并发 / 全局状态 | 一次 `run_file` / `run_text` 只碰自己那份 `Result`；同一个 `Preprocessor` 可以反复用，每次处理互不干扰 |

## 4. 关键实现

### 4.1 按字节工作：下标是字节，切片必须落在字符边界

C++ 的 `std::string` 是字节序列，`preprocess.cpp` 里所有下标（`contentIndex`、
表达式列号、`index_`）都是**字节**偏移；输入里又确实有中文（诊断消息、`%error "炸了"`）。
Rust 的 `String` 是 UTF-8，`s[i]` 根本取不到字节，`&s[a..b]` 又会在非字符边界上 panic。

处理办法是**保持字节语义**，但把每个切点都约束在 ASCII 分隔符上：

- 取字节用 `text.as_bytes().get(i)`（`text::byte_at`），越界给 `0`；
- 找位置用 `str::find` / `rfind`（返回的字节下标**一定**是字符边界）；
- 切片只出现在这些位置：`%`/`#` 之后、名字（`[A-Za-z0-9_]`，纯 ASCII）之后、
  `/`、`\n`、`=`、空白、引号之后——逐个都必然是边界；
- 逐字节扫描的地方（字符串字面量、表达式）只 `+= 1` 移动下标，不切片；
- **唯一要按字节「拼」的地方**是表达式里的带转义字面量：C++ 是
  `value.push_back(text_[index_++])`（推一个字节），Rust 推单个字节进 `String`
  会切坏字符。所以 `parse_literal` 先收进 `Vec<u8>`，出来再
  `String::from_utf8_lossy` —— 与 C++ 逐字节等价（输入本身是合法 UTF-8，且被吃掉的
  `\` 是 ASCII，所以结果必然合法）。

这样 `%error "炸了"` 的诊断消息、`%symbol 中文 值` 被当成内容行（中文不是合法符号名、
于是整行不是指令）这些行为都与 C++ 版一致——`cn.pp` / `cn-hash` 两组对照就是盯这件事的。

### 4.2 符号表：带比较器的 `std::map` → 键归一化 + 哈希表

C++ 用 `std::map<std::string, std::string, SymbolLess>`，`SymbolLess` 在
`caseInsensitive` 时比小写形式。Rust 换成 `HashMap` + **键归一化**：

```rust
fn symbol_key<'k>(name: &'k str, case_insensitive: bool) -> Cow<'k, str> { … }
```

行为等价，因为这张表**只用来查、从不遍历**（`insert` / `remove` / `get`），所以
「`DEBUG` 与 `debug` 视为同一个键」这件事的可观察后果完全一样，而迭代顺序根本不可见。
公开的 `Preprocessor::evaluate()` 收的是一张普通 `HashMap<String, String>`（与 C++
版一样**不**受 `case_insensitive` 影响）。

### 4.3 表达式求值器：两个出参 → 一个错误结构

C++ 的签名是 `bool run(bool &value, std::string &error, std::size_t &column)`，
内部用「`error` 非空即失败」当控制流（`if (!error.empty()) return false;`）。
Rust 版把这套原样搬进结构体字段：

```rust
struct ExprParser<'a, F> { text: &'a str, lookup: F, index: usize,
                           last_value: String, error: Option<ExprError> }
```

`fail()` 仍然「只在还没有失败时记第一处」，各级 `parse_*` 仍然「出错就返回 false 并
不再继续」。对外只暴露 `run() -> Result<bool, ExprError>`，`Preprocessor::evaluate()`
再把它翻成 `Result<bool, Diagnostic>`（`code = "bad-expression"`，`column` 相对表达式）。

**符号查询**：C++ 是 `std::function<bool(const std::string &, std::string *)>`——
第二个参数是「顺便取值」的出参，传 `nullptr` 表示只问「在不在」。Rust 版用
`F: Fn(&str) -> Option<String>`：`Some/None` 就是「在不在」，值也在里面。
`defined(NAME)` 只要 `is_some()`，`NAME == 值` 顺手拿到值——一个类型表达两件事。

### 4.4 `eat` 的副作用必须照抄

`ExprParser::eat(token)` 与 C++ 一样：**先跳空白，再匹配，失败也不回退空白**。于是
`parse_compare` 里那个 `else { index_ = save; return left; }` 不是装饰——它负责把
`eat("==")` 失败时吃掉的空白退回去。这在 Rust 里同样是**必要**的，抄的时候不能
"顺手优化"成无副作用的 `peek`：`%if !( A && B )` 这类用例（对照里的 `deep.pp`）
结果会变。

### 4.5 条件栈与借用：`frames` 不在 `self` 上

C++ 的 `processSource` 里 `std::vector<CondFrame> frames` 是局部变量，
`handleDirective` 收它的引用。Rust 版保留这个形状：

```rust
fn process_source(&mut self, text: &str, file: &str, base_dir: &str, depth: usize) {
    let mut frames: Vec<CondFrame> = Vec::new();
    …
    self.handle_directive(line, &info, file, line_number, base_dir, depth, &mut frames)
}
fn handle_directive(&mut self, …, frames: &mut Vec<CondFrame>) -> bool { … }
```

关键好处是**借用不打架**：`%else` 分支要一边改 `frames.last_mut()`、一边
`self.report(...)` 记诊断，如果 `frames` 是 `self` 的字段就会同时出现可变借用的冲突。
把它放在栈上（`frames` 是独立借用）就天然分开了。代价是给 `handle_directive` 挂了
`#[allow(clippy::too_many_arguments)]`——参数与 C++ 那个函数一一对应，拆结构体只会
让两边对照变难。

同理，`include` 递归展开时 `handle_include` 里 `&self.options.include_loader` 的不可变
借用与随后 `self.report(...)` 的可变借用要能共存：调用 loader 的那段放在单独表达式里，
借用一结束就 `self.report`（NLL 处理得掉）。

### 4.6 `include` 的九步与「标识」的三种来源

`handle_include` 严格照 C++ 的九步走（语法 → 找路径 → 问 loader → 定正文与标识 →
深度 → 循环 → 去重 → 取正文 → 递归），其中第 4 步是容易错的地方：**标识 `label`
有三个来源**——

| loader 返回 | `label` |
| --- | --- |
| `Inline` | 回调给的，留空则 `resolvedPath`，再留空则指令里的原文路径 |
| `UseFile` | 回调给的，留空则 `resolvedPath` |
| 其它（`Default`） | `resolvedPath` |

这个 `label` 同时决定依赖表、去重集合（`included_once`）与循环检测（`include_stack`）
认的是谁。C++ 的测试用 `inline_text(generated, "<csv:stations.csv>")` 显式给标签，
所以「`<csv:...>` 出现在依赖表里」是一条能证伪的断言——Rust 版同样通过。

另外两处细节照抄：**无论这次是否去重都要记 `included_once`**（否则文件自己在正文里
写 `%once` / `#pragma once` 时，第二次包含会漏掉去重）；换文件前后各清一次
`last_marker_file`（前一次让被包含内容强制插 `#line`，后一次让回来的那一行也插）。

### 4.7 行号：空行占位 + 来源表 + 可选 `#line`

`emit_line` / `emit_dropped` 是两条出口，都与 C++ 逐字对应：

- `emit_line`：必要时先插一条 `#line 行号 "文件"`，**这一条也占一行**（所以 `line_map`
  与 `lines_out` 都要 +1），然后写正文 + `\n`；
- `emit_dropped`：`preserve_lines` 打开时写一个空行（并记来源），关掉就什么都不写。

因为都是 `push('\n')` 结尾，**输出末尾一定有换行**——`notrail.pp`（输入无结尾换行）
在对照里就是盯这个。

### 4.8 CLI：一个本地宏顶替 C++ 的 `takeValue` lambda

C++ 的 `takeValue` 是拿 `index` 的引用、可能吃掉下一个 argv 的 lambda。Rust 里在
参数循环体内定义一个 `macro_rules! take_value`，直接展开成「取值 or 报错退出 2」，
再配合循环末尾统一的 `index += 1`，与 C++ `for (…; ++index)` 的推进节奏完全一致
（被 `--opt value` 吃掉的参数不会重复处理）。`--csv-to-lines` 的 CSV loader 与
`main.cpp` 里的演示实现同规则：只接管 `%import` 的 `.csv`，首行当表头，逐行生成
`rowN 列=值 列=值`。

### 4.9 `Result` 同名：一笔明账

结果类型**故意**叫 `Result`，与 `preprocess::Result` 同名，好处是两边的类型名一一对应
（`Define` / `IncludeRequest` / `Options` / `Diagnostic` / `LineOrigin` / `Result`），
写文档和对照代码时不用来回换算。代价是：在 `use preprocess::Result;` 之后，
裸 `Result<(), E>` 指向的是它，标准库那个要写 `std::result::Result`。

crate 内部的规避办法：`lib.rs` 里需要标准库 `Result` 的两处
（`parse_define` / `evaluate`）**显式写全路径**；`engine.rs` / `expr.rs` / `text.rs`
**不** `use crate::Result`，所以它们里面的 `Result<…>` 仍然是标准库那个。README 里也
把这条写在了显眼位置。这是整个移植里**唯一**为了「两边对得上号」而保留的非惯用命名。

## 5. 类型与语义映射（C++ → Rust）

| C++ | Rust | 说明 |
| --- | --- | --- |
| `std::string` | `String` / `&str` | 空串 = 空串，没有 `nullopt` 之说 |
| `bool` + 出参 | 返回值 / `Option` / `Result` | 见 §4.3 |
| `std::vector<T>` | `Vec<T>` | `dependencies` / `diagnostics` / `line_map` / `defines` / `include_dirs` |
| `std::map<std::string,std::string,SymbolLess>` | `HashMap<String,String>` + 键归一化 | 见 §4.2 |
| `std::set<std::string>` | `HashSet<String>` | `included_once` / `once_files` |
| `std::function<IncludeResult(const IncludeRequest&)>` | `IncludeLoader = Box<dyn Fn(&IncludeRequest) -> IncludeResult>` | 别名见 `lib.rs` |
| `IncludeResult::Action`（嵌套 enum） | `IncludeAction`（顶层 enum，`#[derive(Default)]` + `#[default] Default`） | Rust 没有嵌套类型，提到顶层 |
| `useFile(label = "")` / `inlineText(text, label = "")` | `use_file()` / `use_file_as(label)`、`inline_text(text)` / `inline_text_as(text, label)` | Rust 没有默认参数 |
| `Diagnostic::toString()` | `impl Display for Diagnostic`（另留 `to_text()`） | `eprintln!("{d}")` 就能用 |
| `struct Options` 的默认值 | `impl Default for Options` | `include_loader` 是 `Option<Box<dyn Fn…>>`，所以 `Options` **不**能 `derive(Clone/Debug)`——一次处理也只需要借用，不需要克隆 |
| `static bool parseDefine(...)` | `Preprocessor::parse_define(...)` | 关联函数 |
| `std::ifstream` 判定「文件在不在」 | `fs::File::open(path).is_ok()` | 与 C++ 同为「能不能打开」而不是「路径存不存在」（目录在 Windows 上打不开） |
| 读文件到 `std::string`（不校验编码） | `fs::read` + `String::from_utf8_lossy` | 非法字节按 U+FFFD 替换，**不报错**——与 C++ 的「字节照收」一样不会因为编码失败 |
| `%` 前缀判定 `.find(ch) != npos` | `prefixes.as_bytes().contains(&byte)` | 按字节比，不经过 char |

### 6.2 与 C++ 版的 CLI 逐字节对照

`tmp/pp_rust_parity.sh` 在**同一批输入、同一批参数**下分别跑
`build/preprocess/preprocess` 与 `build/preprocess/rust/debug/preprocess-cli.exe`，
比较四件事：`-o` 产物（逐字节）、stdout、stderr、退出码。实测结果：

## 7. 已知边界与差异

### 7.1 三处**有意**的不同（都可复现）

| 项 | C++ 版 | Rust 版 | 为什么 |
| --- | --- | --- | --- |
| `--max-depth abc` | `std::stoul` 抛 `invalid_argument`，没人接 → 进程终止（退出码 3） | 当成用法错误打印 `--max-depth 只接受非负整数`，退出码 2 | 移植时不做「把 C++ 的未定义行为也照搬」。这是**唯一**行为可见的分歧，脚本里单独打印出来 |
| 写 stdout 的换行 | Windows 上 `std::cout` 文本模式 → `CRLF` | Rust 不做换行翻译 → `LF` | 平台产物差异，不是逻辑差异；用 `-o` 两边输出完全相同 |
| `--version` 的串 | `preprocess 1.0（ParseEngine library/preprocess）` | `preprocess-rust 1.0（ParseEngine library/preprocess-rust）` | 名字不同本来就该打不同的版本串 |

### 7.2 值不得当「改进」的地方

- **不把字节下标改成字符下标**：改了以后中文行内列号、`contentIndex` 的语义就与
  C++ 版分叉，两边报错位置会对不上（§4.1）。
- **不给 `Options` 加 `Clone`**：因为 `include_loader` 是 `Box<dyn Fn>`。C++ 里
  `Engine` 是**拷贝**一份 `options_` 的；Rust 版改成「按引用借用」——对一个不可变的
  选项表来说这是纯收益，也不改变可观察行为。
- **不把 `Result` 改名**：见 §4.9，两边类型名一一对应是这次移植的主要便利来源。
- **不动 `eat` 的副作用**：见 §4.4。

### 7.3 没做的（与 C++ 版一致的边界）

不做宏展开、不做表达式算术、不校验被引用的外部文件、不提供「多文件并行处理 API」。
理由都在 §1 的表里。另外 C++ 版的 `Options::includeLoader` 是**同步**回调，
Rust 版同样是同步的 `Fn`，没有引入 `async` 或线程池。
